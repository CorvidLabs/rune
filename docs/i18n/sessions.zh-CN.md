# 持久会话(`rune session`)

`rune run` 会启动一个命令,缓冲其全部输出,然后一次性返回。`rune watch` 可以实时流式传输一个会话,但要求 stdin 上必须连接一个真实的人类终端。这两者都无法跨多次 `rune` 调用让一个 REPL 形态的子进程保持运行——因此,agent 此前没有办法做到:*启动 `codex`、发送一条提示词、等待回答、再发送追问。*

`rune session` 补上了这一块。命名会话的子进程在启动它的 `rune` 调用结束后仍然存活,而且 `send` 会一直阻塞,直到子进程真正给出回答。

## 命名:每个会话都有一个名字,但你很少需要亲自起

会话按**目录**划分命名空间:一个项目由工作目录的基名加上其路径的哈希值组成,因此同一仓库的两个 git worktree 是两个独立的命名空间。`start` 会报告它注册到了哪个命名空间,而读一下这个字段,就决定了你是绕五分钟的弯路,还是耗掉一个小时:

```console
$ rune session start --name reviewer -- grok
{"name":"reviewer","project":"myrepo-0a922f34","command":["grok"],"state":"running",...}
```

在错误的目录里执行 `read`,得到的回答是*"No such session"*;而这个报错所建议的 `list` 会显示一个空数组——看起来像是确认会话已经挂掉了,而不是你正站在别的目录里。

```console
$ rune session start -- grok
{"name":"grok-amber","command":["grok"],"child_pid":68012,"supervisor_pid":67926,"state":"running"}
```

省略 `--name`,rune 会生成一个未占用的 `<tool>-<word>` 代号。这件事比听上去更重要:一旦同时存在两个 grok 会话,"那个 grok 会话"这种说法就毫无意义了,而一个 agent 在启动会话时也不该被迫现编标识符。想自己选名字时,传 `--name reviewer` 即可。

名字的**作用域是项目**——即所在的 git 工作树;不在 git 仓库里时就是目录本身。一个检出里的 `reviewer` 和另一个检出里的 `reviewer` 是两个不同的会话,从错误的目录里都访问不到:

```console
$ rune session list                  # this project only
$ rune session list --all-projects   # everything, labelled by project
```

## 循环

```console
$ rune session start --name grok -- grok
{"name":"grok","command":["grok"],"child_pid":68012,"supervisor_pid":67926,"state":"running"}
```

**`start` 成功并不代表子进程真的在运行。** 如果命令不存在,回复仍然是 `status: "ok"`,`rune` 也依然以 0 退出——只是响应体里带着 `state: "exited"` 和 `exit_code: 127`。start 这个动作本身成功了;是子进程立刻死掉了。要检查的是 `state`,而不是进程退出状态码。

`start` 会立即返回,`rune` 进程随即退出。`grok` 继续运行,由一个持有其 pty 的分离式 supervisor 负责看管。

```console
$ rune session send --name grok --settle-ms 2500 "reply with exactly the word PONG"
```

`send` 会写入提示词,等待 grok 停止输出满 2.5 秒,然后**只返回这次发送所产生的输出**。状态在多次调用之间是持久的,因为每次都是同一个子进程:

拼错的选项会被拒绝,而不是照原样敲给子进程。`send --name grok --settle_ms 500 'echo HELLO'`(下划线,不是短横线)在以前匹配不到任何选项,于是这个选项、它的值和提示词会被拼成一行写入 agent——返回 `status: ok`,结果是一个付费模型在回答 `--settle_ms 500 echo HELLO` 这句话本身。这项检查只看第一个操作数之前、以及任何 `--` 之前的词元,所以 `start --name x claude --resume` 仍能带着自己的选项启动 agent,`send --name x -- --settle_ms` 也仍会把 `--settle_ms` 当作字面输入敲进去。

```console
$ rune session send --name s --settle-ms 300 "MEMORY=persisted"
$ rune session send --name s --settle-ms 300 'echo "value=$MEMORY"'
value=persisted
```

```console
$ rune session list
● grok-amber  running  idle 3s   grok
    Thought for 1s
● worker      running  idle 2m   bash --norc -i
    bash-3.2$

$ rune session stop --name grok-amber
```

每一行都带着这个会话已经安静了多久、以及它最后打印的一行内容——当多个 agent 同时运行时,这是回答*这个会话是在干活还是卡住了、它正在做什么?*最快的方式。同样的字段(`idle_ms`、`last_line`)在 `--json` 里也有。

## 接管方向盘,再交还回去

```console
$ rune session attach --name grok-amber
[rune session] attached — Ctrl-] to detach (session keeps running)
```

`attach` 会把你真实的终端接到一个正在运行的会话上:输出流式显示到你的屏幕上,你的按键直接发给 agent,连接时会重放当前屏幕,免得你对着一片空白;同时**子进程会被调整为你的终端尺寸**(并且在你调整窗口大小时跟随变化),这样全屏 agent 会按你的窗口布局,而不是按无头模式下的默认尺寸。当你脱离(detach)时,子进程会回到默认尺寸,所以无论你是否 attach 过,程序化的 `send` 渲染出来的结果都是一样的。**Ctrl-]** 会脱离并让一切继续运行——这就是它与 `rune watch` 的全部区别,后者拥有自己启动的子进程。Ctrl-C 被刻意保留,*不是*脱离键:它必须继续传给子进程,这样你才能打断一个失控的 agent。

## 归档

停止后的会话会一直占用它的名字,还会让 `list` 显得杂乱。把它归档:

```console
$ rune session stop --name reviewer
$ rune session archive --name reviewer
$ rune session list --archived
```

归档会释放这个名字,并把会话记录转存到项目的归档目录下。已归档的会话不在 `read` 的可达范围之内——对它执行 `read --name` 会报告会话不存在——所以任何还想要的东西,都要在归档*之前*取出来。已归档的会话绝不可能被误认为存活会话,而且复用这个名字时会是真正意义上的全新开始——`start` 会重置会话记录,使 `send` 游标和 `read` 偏移量始终描述同一个生命周期。

## 如何知道对方 agent 已经做完了

这是最难的部分,rune 按推荐顺序给了你三个工具。

**`--settle-ms N`(默认 800)**——等子进程安静满 N 毫秒后返回。这是主要的判断信号。settle 计时器只在收到非"pty 对你自己输入的回显"的输出之后才开始走,所以一个先回显你的提示词、然后思考再作答的 agent,返回的是答案,而不是把你自己的话原样吐回来。

> **一个始终没有提交的提示词,看起来和上面一模一样,但那是另一个 bug。** rune 会先写入一次 send 的文本,稍过片刻再把回车符作为*单独一次*写入,因为如果把两者一起读进去,TUI 会把回车当作文本的一部分,从而永远不提交。这个延迟是一场无法被观测的竞态:对 Kimi 实测,旧的 0.05 秒延迟下 3 次发送全部失败——提示词停在输入框里,`send` 返回 `settled: true` 且只有回显,而子进程还在等一个其实已经写入的按键。现在是 0.25 秒,Claude Code、grok 和 Kimi 都能正常提交。如果你遇到更慢的 TUI,判断方法是 `read --screen` 会显示你的文本还停在输入框里:发送一个空字符串,单独送出一个回车符,它就会提交。

> **已知限制,也是目前 rune 里最棘手的一个:会*重绘*你输入内容的子进程,仍然可能在回显上 settle。** 上面那条规则只在回显只到达一次时成立。行编辑器在提交时会重绘整行,把你的输入再发一遍,而这第二份拷贝会被算作"子进程说话了"。用 `--settle-ms 800` 实测:`irb` 和 `python3 -q` 各自 3 次里有 3 次在大约一秒内返回 `settled: true`,内容只有回显,而真正的答案几秒后才到,落进*下一次*调用捕获到的内容里。普通的 `bash -i` 不受影响,包括超出终端宽度折行的输入。
>
> **回复里没有任何东西能把这种情况和真实答案区分开**——`settled: true`、`busy_at_send: false`,而且回显本来就合法地属于一条正确回复的一部分。在修复之前,用 `--wait-for-regex` 来驱动会重绘的 REPL(它不受影响),或者检查回复里是否包含超出你所发送内容的东西。

**`--wait-for-regex RE`**——输出一旦匹配就立即返回。这是确定性的做法,只要你知道被调用方完成时会打印什么,它就是正确答案:

```console
$ rune session send --name s --wait-for-regex '\$ $' "ls"
```

> **模式匹配的是回复内容,而不是你输入的回显。** pty 会回显你写入的内容,所以一个 naive 的实现会在你自己的话刚一回来时就返回。rune 在*压缩*文本中定位回显——两侧都去掉了转义序列和空白,这正是"你发送的内容"与我们能捕获到的各种变形回显之间的差别——并且会否决一个被输入的重绘拷贝所覆盖的匹配。对 `python3 -q` 实测(它的 REPL 每敲一个键就重绘一次):以前它会在 0.22 秒内返回 `matched: true`,比代码真正运行早了八秒,4 次里有 4 次如此;现在它会等到真实输出,3 次里有 3 次如此。
>
> 诚实的说法是:*我们能从真实子进程捕获到的每一种回显形态都被排除了*,而不是*绝不可能发生*。如果你的模式是一个你自己也发送过的字面量,一个把你的请求原样引用回来的子进程仍然可能满足它。否决机制还需要*看到*那份拷贝:如果一次重绘被 pty 的读取撕成两半——帧在重绘中途结束,剩下的部分在下一次读取才到达——它还无法被识别为拷贝,于是一个只出现在你自己输入里的模式可能被这一半满足。把帧恰好在该词元之后切开,就能确定性地复现这种情况。所以,凡是也出现在你所发送内容里的模式,仍然是应该避免的形态。

> **模式所匹配的输出范围:回显之后最近的 256 KB,每次读取时向前回看 32768 个字符。** 这是一个有意设定的边界,带来两个后果。
>
> - **长度不超过 32768 个字符的单次匹配总能被找到**,无论这一轮输出增长到多大,因为每次扫描都会从上一次停止的位置向前回看这么远。任何你真正会等待的东西——标记符、提示符、闭合围栏——都远远在这个范围之内。
> - **必须跨越 32768 个字符以上的单次匹配永远找不到。** 横跨半 MB 的 `OPEN[\s\S]*CLOSE` 以前能匹配,现在不能;send 会继续运行,直到 `--settle-ms` 或 `--timeout-ms` 触发。应该单独等待 `CLOSE`,需要两者之间的内容时用 `read` 取。
>
> `\A` 仍然锚定在子进程回答的开头,而不是窗口的开头——锚定模式不会被窗口恰好开始的位置所满足。`^`、`$` 和 `\z` 不受影响。**回复本身不受这些限制约束:** `output` 仍然是子进程在这一轮产生的全部内容。
>
> 正是这个边界让超长答案变得可以企及。以前,模式会在每次 4 KB 读取时对整轮输出做匹配,这对整轮长度来说是平方级开销——而且发生在 supervisor 唯一的线程上,因此还会饿死 pty 的排空。对一个先输出 N MB、再打印一个标记符的子进程实测,模式用的就是同一个标记符:
>
> | 输出量 | 修改前 | 修改后 |
> | --- | --- | --- |
> | 4 MB | 11.85s,matched | 0.53s,matched |
> | 12 MB | 90.51s,`timed_out: true`,12.00 MB 中只读到 11.46 MB | 0.98s,matched,读到 12.15 MB |
> | 48 MB | 112.43s,matched | 3.37s,matched |
>
> 在 12 MB 那档,send 报告了超时,而它手里已经握着一份答案的 96%——答案的标记符,子进程早就打印出来了。

**`--timeout-ms N`(默认 120000)**——硬性上限。到期时你会拿到已捕获的内容,外加 `settled: false, timed_out: true`——这是一个结果,而不是失败。要有意识地设置它:默认值给得很宽松,因为 agent 很慢,所以一次手误的调用要花掉两分钟。

`--no-wait` 写入后立即返回,适用于你根本不期待回复的场景。它的回复是另一种形态——`{action, name, sent: true, waited: false}`,没有 `output`、`cursor` 或 `prompt_detected`,因为没有等待任何东西。

`--no-newline` 只写入文本,不带那个用来提交的尾随回车符,适合把一行内容分段拼出来,或者驱动一个按按键读取的 TUI。

### 回复里的其他字段

- `settled: true`——**这次等待得到了回应,而不是超时结束。** 有三种不同的情况会置上它,伴随字段会告诉你是哪一种:子进程在 settle 窗口内安静下来(没有伴随字段);`--wait-for-regex` 匹配成功(`matched: true`);或者子进程退出了(`child_exited: true`)。它**本身并不**意味着子进程安静下来了——正则匹配在完全没有安静期的情况下也会置上它,这就是为什么一条回复可以在 60 秒 settle 窗口才过 0.45 秒时就带着 `settled: true`。

  在它*确实*表示安静的地方,安静有三种成因,而这个字段无法区分:这一轮做完了;子进程在等人类操作;或者**子进程把一条长命令放到了后台,停止打印了**。第三种情况才是真正会咬人的:一个轮询"忙碌标记是否消失"的调用方,读到一帧没有标记的画面,就断定工作完成了——比真正完成早了 260 秒。如果你要依据某样东西的*缺失*来做判断,光有 `settled` 是不够的。
- `timed_out: true`——先触到了 `--timeout-ms`。这是一个结果,不是失败。
- `matched: true`——`--wait-for-regex` 匹配成功。
- `child_exited: true`——子进程在这次 send 进行期间结束了。
- `busy_at_send: true`——这次 send 到达时,子进程*仍在产生输出*,所以回复里可能带着上一轮的尾巴。如果某个答案看起来像是属于上一个问题的,值得查一下这个字段。
- `regex_timed_out: true`——`--wait-for-regex` 的模式超出了匹配预算,被放弃了。几乎总是灾难性回溯的模式;把它简化。
- `dropped_bytes`——日志中已不再保留的早前输出的字节数:要么被轮转了,要么因为一次会话记录写入失败而丢失。它**不会**让 `--since` 游标失效:游标始终是绝对的,所以一个位于丢弃点之前的游标,返回的是丢弃点*之后*仍然保留的全部内容,而不是报错。落在已丢弃区间内的游标,会解析到该区间之后的输出——绝不会解析到已经投递过的输出,否则那些内容会以"本轮新输出"的面貌再次出现。
- `transcript_gap_bytes`——只出现在 `status` 和 `send` 的回复上,且只在仍有"任何写入都没能记录"的输出欠着的时候出现。这是唯一一个偏差尚未落盘的窗口:下一次写入成功时会把它记下来,此后 `read` 会以 `dropped_bytes` 的形式报告它。
- `screen_rows`、`screen_cols`、`screen_size_recorded`——只在带 `--screen` 时出现:屏幕渲染所用的几何尺寸,以及该几何尺寸是子进程记录在案的 winsize 还是回退默认值。参见[按子进程实际运行的尺寸渲染](#按子进程实际运行的尺寸渲染)。

### `child_busy` 和 `idle_ms` 在 `read` 上,不在 `send` 上

子进程在 settle 窗口内是否打印过任何东西,以及距离它上次打印过去了多久。这是"它还在干活吗"的结构化形式:用它,而不是去被调用方自己的 UI 里 grep 忙碌标记——那是展示层的东西,会毫无预兆地变化。

**它们是 `read` 和 `list` 的字段,不是 `send` 回复的字段。** `send` 本身已经阻塞到子进程 settle 了,所以在事后去问:

```console
$ rune session send --name grok --settle-ms 2500 "run the suite"
$ rune session read --name grok --tail 1 --json     # child_busy, idle_ms
```

本文档以前曾把这两个字段列在 `send` 回复的字段里,这个错误恰恰错在最要命的地方——一个从 `send` 回复里读 `.child_busy` 的调用方拿到的是 `nil`,于是退回到 grep UI 的老路,而这正是这两个字段存在所要取代的做法。

注意,这个名字说的是子进程在*打印*,而不是在*工作*:一个把命令放到后台然后安静下来的子进程,报告的是 `child_busy: false`。

### 在长长的会话记录里查找内容

当你要的东西在中间位置时,`--since` 和 `--tail` 都帮不上忙。和一个被驱动的 agent 干一天活,记录能到 379KB。

```console
$ rune session read --name grok --grep 'THE BOARD' --context 2
```

它匹配的是*清理后*的文本,而不是原始字节流,因为全屏 agent 的重绘帧会把单词拆散在转义序列之间——一个你在屏幕上明明看得见的模式,在字节里却匹配不到。回复里带着 `grep_matches`。

**清理不等于渲染,而这个差别恰恰会在 session 存在所要驱动的那类子进程身上咬人。** 清理后的文本是去掉转义序列后的完整重绘流,所以:被覆盖掉的历史内容仍然能匹配,并作为一条干净的独立行返回,尽管屏幕早就不再显示它了;光标绘制的帧完全没有换行符,所以它是单独一条 grep 行,`--context` 不起作用,一次匹配会把整个帧返回回来,顶上还挂着一个看起来挺正常的 `grep_matches: 1`;而一个锚定在"你在屏幕上能看到的东西"上的模式可能返回 `grep_matches: 0`,因为屏幕上的相邻不等于流里的相邻。当问题是*此刻显示的是什么*时,用 `--screen`。`--grep` 是用来在长记录里找某一行内容的,这正是它擅长的事。

编译不通过的模式会以 `grep_error` 的形式返回,而不是抛异常,并且**什么都选不中**:`output` 和 `clean_output` 是空的,`grep_matches` 也不存在——这就是你区分"过滤器根本没运行"和"过滤器什么都没找到"的方法。read 本身仍然成功,所以 `cursor`、`prompt_detected` 和 `child_busy` 都还在——它们都不依赖那个模式,而且你需要游标才能继续推进。(`send --wait-for-regex` 不一样:在那里模式决定何时返回,所以坏模式会被直接拒绝。)

### `prompt_detected` 仅供参考

每个 `send`/`read` 结果都带着 `prompt_detected`,但**不要用它做门控**,而且要清楚它会往哪个方向出错。

对真实输出实测:纯文本时是 `false`,光秃秃的 `$ ` 时是 `false`,**`Do you want to proceed?` 时也是 `false`**,而 `❯ ` 时是 `true`。所以对 grok 来说,它几乎每次 read 都是 `true`,因为 grok 的输入框总是以 `❯` 结尾——有个调用方看到它 8 次里有 8 次是 `true`,就断定它没有任何区分度。它是有区分度的;它只是在做*检测长得像提示符的最后一行*,这和"它是否在等我"不是同一个问题。注意上面第三种情况:对你最想让它抓住的那个权限确认对话框,它恰恰是 `false`。那种情况要看屏幕。rune 的提示符模式匹配的是 shell 形态的提示符(`user@host:~$`、`[y/N]`、`Password:`),而且刻意做得很保守。Agent REPL 大多一个都不像,所以对你最想驱动的那批 CLI,它通常就是 `false`。等待提示符在大多数真实目标上都会挂起——这正是 settle 时间成为主要信号的原因。

## 读取会话记录

`read` 会重放会话的持久记录,无论会话是活着还是已经停止,行为都一样:

```console
$ rune session read --name grok --tail 50
$ rune session read --name grok --since 41234     # page from a cursor a previous call returned
```

每个会话都会写一份 NDJSON 事件日志,格式与 `rune watch` 产生的相同,所以你可以在另一个窗格里跟踪一个活着的会话:

```console
$ tail -f ~/.rune/projects/<project>/sessions/grok/output.ndjson
```

全屏 TUI agent 会产生大量 ANSI 重绘流量,所以请优先用 `--tail`/`--max-output`,而不是整份记录全读。

`--max-output=BYTES` 会保留一段开头和一段结尾,并在文本本身里标出拼接处:

```
...the last line before the cut
[rune] ==== 41233 bytes omitted by --max-output ====
the first line after it...
```

没有这一行标记,回复读起来就像一段子进程从未打印过的连续输出——实测过:一份 201 字节的记录配 `--max-output=200`,恰好丢掉的那一个字节把 `chsh -s /bin/zsh` 变成了 `chsh -s bin/zsh`,那是一条不同的、但照样说得通的路径。这个标记是 rune 加的注解,不属于会话记录,所以它不占 BYTES 的额度,一条回复可能略微超出预算;`truncated` 和 `omitted_bytes` 仍然是权威答案,因为子进程什么都能打印,包括一行长得和标记一模一样的东西。

### `--screen`:终端上显示的内容,而不是到达过的内容

对于全屏 agent,这通常就是你想要的字段。字节流里装着每一次重绘的每一帧,答案被拆散在其中;而屏幕里只有当前显示的东西。

```console
$ rune session send --name grok --screen -- "reply with just the branch name"
$ rune session read --name grok --screen
```

对 grok 实测:一份 361KB 的记录渲染出来只有 1.1KB 的屏幕;一个 agent 明明白白显示出来的答案,**在 3 轮里有 3 轮缺席于字节流,而在 3 轮里有 3 轮出现在渲染后的屏幕里**。如果你要按内容做匹配,就在 `screen` 上匹配。

有三件事它不是。它是*终态*,所以任何滚走的内容都没了——"发生了什么"的记录仍然是会话记录(transcript)。它是可选开启的,因为只有对会绘制屏幕的子进程它才有意义:对一个 cooked 模式的 shell,字节流本身就是答案。还有,它**不受 read 过滤器约束**——`--since`、`--tail`、`--grep` 和 `--max-output` 约束的都是 `output`/`clean_output`,对 `screen` 一概不管。它也是有界的,只是边界来自几何尺寸:最多 `screen_rows x (screen_cols + 1)`,这两个值都在同一条回复里返回。一份 219,941 字节的记录,渲染出来大约 2KB。所以 `--max-output=200 --screen` 给你的是一条有界的回复,只不过约束它的是一条你没有点名的规则。

### 按子进程实际运行的尺寸渲染

会话的子进程以 40x120 启动,而 `attach` 会把它调整成接管它的那个终端的尺寸——所以尺寸不是常量,按某个固定尺寸渲染,得到的屏幕是谁都没见过的。supervisor 每次改变子进程尺寸时,都会把当前的 winsize 记进 `meta.json`,`--screen` 就按这个尺寸渲染,并把它报告回来:

```console
$ rune session read --name grok --screen --json | jq '{screen_rows, screen_cols, screen_size_recorded}'
{ "screen_rows": 30, "screen_cols": 100, "screen_size_recorded": true }
```

端到端实测,用 pyte 0.8.2 和 GNU screen 4.00.03 重放同样的字节,作为相互独立的参照系(在每一种尺寸下,两者的结果都完全一致):

| 被驱动的内容 | 修改前错行数 | 修改后错行数 |
|---|---|---|
| 通过控制 socket 调整到 30x100,子进程在 WINCH 时重绘 | 36/37 | **0/31** |
| 同上,24x80 | 30/31 | **0/25** |
| 同上,12x40 | 18/19 | **0/13** |
| 同上,50x200 | 50/51 | **0/51** |
| 同上,40x120(尺寸恰好相同) | 0/41 | 0/41 |
| 从一个 30x100 的 pty 执行真实的 `rune session attach`,子进程忽略 WINCH | 29/30 | **0/30** |

在 attach 那一行,喂给参照系的正是那个终端自己收到的字节,所以"30 行里错 0 行"意味着 rune 渲染出的屏幕与人类当时所看到的逐行一致。

**区分真实几何尺寸和回退默认值,靠的是 `screen_size_recorded`,而不是数字本身。** 从一个 40 行的终端 attach 过来的会话,记录下来的恰好也是回退值所用的 40x120,所以光靠这一对数字无法区分。只有当报告的尺寸确实是 `meta.json` 里实际记录的内容时,`screen_size_recorded` 才为 true。它在三种情况下为 false,这三种情况报告的都是 40x120:

- 没有人调整过尺寸的会话。supervisor 把 pty 设为 40x120 且不做记录,所以这里的回退值并不是猜测——它就是子进程真正在运行的尺寸。
- 在 rune 开始记录尺寸之前就已写入的会话目录。
- 记录下来的尺寸不是一个可用的终端尺寸,它会被丢弃或钳制,而不是照单分配:`meta.json` 是磁盘上的一个文件,而网格是立即构建的。

通过控制 socket 到达的调整请求会被钳制在 300x1000 以内——已经超出任何真实终端——而且这个钳制既作用于记录,也作用于 pty,所以子进程、记录和渲染三者始终一致。pty 的 winsize 字段是 16 位的,一条 65535x65535 的记录会让之后每一次 `--screen` 都驱动一个那么大的网格:在一份刻意构造的恶意 683KB 记录上,一次 `read --screen` 在 40x120 下耗时 0.76 秒,在钳制上限下耗时 3.41 秒,而没有钳制时是 17.72 秒。

**有一种 resize 情形尚未解决。** 保留下来的整份记录都是按子进程*当前*的尺寸渲染的,所以如果几何尺寸中途变过,变化之前绘制的输出会按新尺寸重新排版。对全屏 agent 来说这是对的,而且可以证明是对的:TUI 收到 SIGWINCH 会重绘,而 attach 时 supervisor 会把积压内容按终端的尺寸重放进终端——这恰好等同于把整份记录按那个尺寸渲染一遍——上面那行"30 行错 0 行"的 attach 实测,即使对完全无视 SIGWINCH 的子进程也成立。尚未解决的是这样一种子进程:它只绘制一次、从不重绘,*而且*它的 pty 随后在一个已经 attach 的终端下被调整了尺寸——因为那个终端正在重排它已经画过的字形,不存在可供比对的参考答案。在这样的字节流上从 40x120 中途缩到 24x80,GNU screen 只保留了光标所在行,pyte 什么都没保留,而两者在仅存的那点内容里还有一行互不一致。rune 保留内容并重新排版,所以和两者都不同。在那里按旧的固定尺寸渲染,原始错行数确实更好看(错 15 行,对 24 行),但那只是因为一个几乎空白的屏幕碰巧对上了一个几乎空白的参照系——而不是因为它给任何人展示了更真实的东西。

**渲染只取最后 512KB,而对某些 agent 这有看得见的代价。** 对 grok 在 4.5MB 输出里的一次普查发现:109,364 次绝对光标移动,31,798 对同步更新括号,而擦除操作是**零**——没有 `\e[K`,没有 `\e[2K`,没有 `\e[2J`,也没有滚动区域。一个纯粹靠定位加覆写来重绘的 agent,依赖终端记住它写过的每一个单元格,无论那是多久以前。从窗口开始渲染则是从一张空白网格起步,所以任何只绘制过一次、再没重绘过的东西——标题栏、横幅——就直接缺席了,而 rune 无从得知它缺了。更频繁地读 `--screen` 无济于事;窗口是按字节算的,不是按时间。

同一份普查还解释了一个更微妙的点。当 agent 从不擦除时,屏幕上出现重复行可能完全忠实于原样:如果它的布局下移了一行,并在新位置重绘,旧的那份没有任何东西去抹掉它,于是**真实终端上也会显示这个重复**。在把重复行当 rune 的 bug 处理之前,先查一下这个 agent 到底擦不擦除任何东西。

### 已知限制:轮询 `--screen` 可能返回画了一半的帧

来自真实使用的报告,**尚未修复**。对一个正在重绘的 agent 轮询 `--screen`,偶尔会返回一个正在重绘中途的帧——在报告的案例里,是一行内容重复出现在相邻两行上。

两个候选修复都经过实测并被否决。比较连续两次渲染、只在结果重复时才返回的做法,实测**比什么都不做更差**——20 次里撕帧 13 次,对照组是 11 次——因为一个按周期绘制的 agent 很少会把同一帧渲染两遍,所以这个检查最终超时,然后照样把撕开的帧交回去。把稳定性重新定义为"静止"则根本无法复现撕帧:同一个子进程一次给出 11/20,两次给出 0/20,这说明测试装置所测量的并不是它看上去在测量的东西。一个悄悄朝着"看起来完成了"方向失败的修复,比一个你可以绕着规划的已知限制更糟糕。

**该怎么应对。** 对于一个无法撤销的决定,不要把某一帧渲染结果当作权威依据。如果你在读一个值,轮询两次并要求两次一致。如果你在等一个标记符,`--wait-for-regex` 是确定性的,而 `--screen` 只是一张快照。

**这可能不是 rune 的错。** 对某 agent 在 4.5MB 输出里的一次普查发现,擦除操作为零;而一个从不擦除、还会移动布局的 agent,会把旧的拷贝留在屏幕上——真实终端也会显示这个重复。在基于该普查构建的六种场景下,rune 的渲染器与一个独立的模拟器结果一致。在把重复行当作 rune 的 bug 上报之前,先查一下这个 agent 到底擦不擦除任何东西。

### 会话记录是有界的

文件和 supervisor 的内存都有上限,所以一个跑了一整天的会话不会无限增长。文件的上限有两道强制:正常情况靠轮转;而当轮转完全无法成功时——目录变得不可写,或者磁盘一直是满的——就启用两倍于上限的硬顶,超过之后输出会被记为丢弃,而不是写入。无论哪种情况,`read` 都会报告 `dropped_bytes`,游标保持绝对。当轮转丢弃较旧的输出时,`read` 报告 `dropped_bytes`,游标保持绝对——游标仍然指向流中的同一个位置,只是那个位置指向的输出已经不再保留。

一次失败的会话记录写入——磁盘满了、目录不可写——会以同样的方式丢弃输出,只不过发生在一条仍在继续的流的*中间*。这些字节会被携带着,在写入恢复后立即记录下来;游标按每一个丢弃区间逐一映射,而不是跨过一个滚动累计值,所以空洞之前的输出不会被当作新输出重复投递。在写入成功之前,磁盘上没有任何地方可以记录这个空洞,这正是 `status` 上 `transcript_gap_bytes` 所报告的内容。

## 驱动真实 agent 之前需要知道的事

- **`start` 返回时,就绪的是 *supervisor*,不是子进程。** Agent CLI 启动要花好几秒,在它开始监听之前送去的输入会直接丢失。在驱动一个刚启动的会话之前,先等一个就绪标志——轮询 `read`,或者让第一次 `send` 带上 `--wait-for-regex`。
- **settle 是启发式判断。** 一个回答中途停顿超过 `--settle-ms` 的子进程,会返回截断的响应。把它调大,或者改用 `--wait-for-regex`。
- **`--wait-for-regex` 看到的是最近 256 KB,而不是整轮输出。** 长度不超过 32768 个字符的任意单次匹配总能找到;必须跨越更长的匹配永远找不到。等一个标记符,而不是等一个框住好几 MB 的模式。
- **一条 1024 字节以上的单行,会在 cooked 模式的子进程那里消失得无影无踪。** 这是 `MAX_CANON`,是终端的限制,不是 rune 的:行规程拼不出更长的规范行,会静默丢弃——1023 字节能到,1024 字节到不了。大多数 agent CLI 让终端运行在 raw 模式,不受影响(300KB 逐字节完好到达)。交互式 shell 也一样:`bash --norc -i` 使用 readline,会把终端置于 raw 模式,1995 个字符的一行逐字节完好接收。会咬人的是以 *cooked* 模式读取的子进程——一个光秃秃的 `cat`,或者一个不用 readline 读 stdin 的脚本。把输入分块,或者驱动一个 raw 模式的目标。
- 回车以 carriage return 的形式发送,这正是真实终端所发送的,所以 raw 模式的 TUI 能收到它。cooked 模式的 shell 不受影响。
- 子进程的 pty 会被显式设置窗口尺寸,因为分离的会话没有终端可供拷贝尺寸,而未设置的 pty 是 0x0——那会让全屏 agent 对着一片虚无渲染。它以 40x120 起步,有终端 attach 期间跟随该终端(上限 300x1000),最后一个终端离开时回到 40x120。`--screen` 按当前生效的那个尺寸渲染。

## 状态存在哪里

`RUNE_HOME`(默认 `~/.rune`),权限为仅所有者可访问:

```
$RUNE_HOME/projects/<project>/
  sessions/<name>/
    meta.json        0600   pid, supervisor pid, command, state, child terminal size
    output.ndjson    0600   full transcript
    supervisor.log   0600   supervisor stderr, for when something goes wrong
    control.sock     0600   the supervisor's control socket
  archive/<stamp>-<name>/   archived sessions, out of the live namespace
```

设置 `RUNE_HOME` 可以让会话相互隔离(测试、沙箱、并行工作)。

`meta.json` 通过 rename 整体替换,从不在原地截断,因为其他每个 rune 进程都会读它来回答"这个会话存在吗、还活着吗",而且没有任何锁可拿。它变短的窗口,就是 `send` 回答 "No such session"、`list` 报告 `state: dead` 的窗口;而记录子进程 winsize 让这个文件变成了每次 resize 都要写一次,人类拖动窗口边缘时每帧都会产生一次。实测:一次真实 attach 在 7.5 秒内拖过 250 种窗口形状,同时另一个进程在紧循环里读 meta——修改前 294,728 次读取里有 90 次读不出来,修改后 312,582 次里 0 次。

## 同时运行多个会话的代价

一个会话对应一个 supervisor 进程,这种隔离是刻意的:一个卡死的 agent 只会拖垮它自己的会话,不会波及其他。代价是每个会话一个 Ruby 解释器,在你大规模铺开之前值得先知道这一点。

实测,子进程均为空闲状态:

| 会话数 | 常驻内存 | 文件描述符 |
|----------|-----------------|-------------|
| 24 | 543 MB | 648 |
| 60 | 1361 MB | 1620 |

也就是**每个会话约 23 MB 内存、27 个文件描述符**,而且是平的——60 个会话和 24 个会话时单价相同,多轮 send 之后也不变。所以这个成本是可预测的线性增长,而不是意外惊吓,但它是前置的:六十个 agent 在任何一个还没干活之前,就要花掉远超 1 GB 的内存。

在同一项测试里,并发本身经受住了考验:60 个同时发起的 start 全部成功,每个 send 都到达了它所指向的会话,`list` 与现实一致,结束后没有任何残留进程。三十个同时发起的、*不带* `--name` 的 `start` 调用(针对同一个工具),产生了三十个互不相同的代号,没有碰撞。

## 边界

rune 是会话的**经纪人**,不是消息总线。它持有会话、按名字寻址;决定谁和谁对话是调用方 agent 自己的事——名字已经在它手里了。跨会话路由、按 agent 划分的配置档案、共享的对话日志,都被刻意排除在边界之外。
