# 永続セッション（`rune session`）

`rune run` はコマンドを起動し、出力をすべてバッファして、一度だけ結果を返します。`rune watch` はセッションをライブでストリームしますが、stdin に実際の人間の端末が必要です。どちらも、REPL 型の子プロセスを別々の `rune` 呼び出しをまたいで開いたままにしておくことはできません。つまりエージェントには「*`codex` を起動し、プロンプトを送り、回答を待ち、続きの質問を送る*」ということができませんでした。

`rune session` がそれを可能にします。名前付きセッションの子プロセスは、それを起動した `rune` の呼び出しよりも長く生き続け、`send` は子プロセスが実際に応答するまでブロックします。

## 名前付け：すべてのセッションに名前はありますが、自分で決める必要はめったにありません

セッションは**ディレクトリ**ごとに名前空間が分かれています。プロジェクトは、作業ディレクトリのベース名にそのパスのハッシュを付けたものなので、同じリポジトリの git worktree が2つあれば、2つの別々の名前空間になります。`start` は登録先の名前空間を報告します。このフィールドを読むかどうかが、5分の寄り道と1時間の寄り道の分かれ目です。

```console
$ rune session start --name reviewer -- grok
{"name":"reviewer","project":"myrepo-0a922f34","command":["grok"],"state":"running",...}
```

違うディレクトリから `read` すると「*No such session*」と返り、そのエラーが促す通りに `list` を実行しても空の配列が表示されます。これは、自分が別の場所にいるのではなく、セッションが死んだように見えてしまいます。

```console
$ rune session start -- grok
{"name":"grok-amber","command":["grok"],"child_pid":68012,"supervisor_pid":67926,"state":"running"}
```

`--name` を省略すると、rune は未使用の `<tool>-<word>` 形式のコードネームを生成します。これは見た目以上に重要です。「あの grok セッション」という言い方は、2つある時点で意味をなさなくなりますし、セッションを立ち上げるエージェントが識別子を考案する必要はないはずです。自分で名前を選びたいときは `--name reviewer` を渡してください。

名前は**プロジェクトにスコープ**されています。プロジェクトとは、外側の git ワーキングツリー、あるいは git の外ではそのディレクトリ自体です。あるチェックアウトの `reviewer` と別のチェックアウトの `reviewer` は別のセッションであり、どちらも間違ったディレクトリからは到達できません。

```console
$ rune session list                  # this project only
$ rune session list --all-projects   # everything, labelled by project
```

## 基本的な流れ

```console
$ rune session start --name grok -- grok
{"name":"grok","command":["grok"],"child_pid":68012,"supervisor_pid":67926,"state":"running"}
```

**`start` が成功しても、子プロセスが動いているとは限りません。** コマンドが存在しない場合でも、応答は `status: "ok"` で、`rune` の終了コードも 0 です。ただし本文には `state: "exited"` と `exit_code: 127` が入っています。start 自体は成功していますが、子プロセスは即座に死んだのです。確認すべきはプロセスの終了ステータスではなく `state` です。

`start` はすぐに制御を返し、`rune` プロセスは終了します。`grok` は、pty を保持するデタッチされたスーパーバイザに所有されて、動き続けます。

```console
$ rune session send --name grok --settle-ms 2500 "reply with exactly the word PONG"
```

`send` はプロンプトを書き込み、grok が 2.5 秒間出力を止めるのを待ってから、**その send が生み出した分だけ**を返します。状態は呼び出し間で持続します。毎回同じ子プロセスだからです。

フラグの打ち間違いは、子プロセスに入力されるのではなく拒否されます。`send --name grok --settle_ms 500 'echo HELLO'`（ダッシュではなくアンダースコア）は、かつてどのフラグにも一致しなかったため、フラグとその値とプロンプトが1行に連結されてエージェントに書き込まれていました。結果は `status: ok` で、有料モデルが `--settle_ms 500 echo HELLO` に回答する羽目になりました。このチェックは最初のオペランドより前、かつ `--` より前のトークンだけを見ます。そのため `start --name x claude --resume` はエージェント固有のフラグ付きで普通に起動できますし、`send --name x -- --settle_ms` は `--settle_ms` をリテラルな入力として打ち込みます。

```console
$ rune session send --name s --settle-ms 300 "MEMORY=persisted"
$ rune session send --name s --settle-ms 300 'echo "value=$MEMORY"'
value=persisted
```

```console
$ rune session list
● grok-amber  running  idle 3s   grok
    Thought for 1s
● worker      running  idle 2m   bash --norc -i
    bash-3.2$

$ rune session stop --name grok-amber
```

各行には、セッションが静かになってからの時間と、最後に出力した行が載っています。複数のエージェントが同時に動いているときに「*この子は動いているのか、詰まっているのか。何をしているのか？*」を知る最速の方法です。同じフィールド（`idle_ms`、`last_line`）は `--json` にも含まれます。

## ハンドルを握り、そして手放す

```console
$ rune session attach --name grok-amber
[rune session] attached — Ctrl-] to detach (session keeps running)
```

`attach` はあなたの実端末を実行中のセッションに接続します。出力は画面にストリームされ、キー入力はエージェントに送られ、接続時には現在の画面がリプレイされるので真っ暗な画面を見つめることになりません。さらに**子プロセスはあなたの端末サイズにリサイズされます**（リサイズにも追従します）。そのためフルスクリーンのエージェントは、ヘッドレスのデフォルトではなく、あなたのウィンドウに合わせてレイアウトします。デタッチすると子プロセスはデフォルトのサイズに戻るので、アタッチしたかどうかにかかわらず、プログラムからの `send` は同じようにレンダリングされます。**Ctrl-]** はデタッチして、すべてを動いたまま残します。これが、自分が spawn した子プロセスを所有する `rune watch` との決定的な違いです。Ctrl-C がデタッチキーで*ない*のは意図的です。Ctrl-C は暴走したエージェントを中断できるよう、子プロセスに届き続ける必要があるからです。

## アーカイブ

停止したセッションは名前が予約されたままで、`list` を散らかします。アーカイブしましょう。

```console
$ rune session stop --name reviewer
$ rune session archive --name reviewer
$ rune session list --archived
```

アーカイブすると名前が解放され、トランスクリプトはプロジェクトのアーカイブに保管されます。アーカイブ済みのセッションは `read` の対象外です。`read --name` を実行してもそのようなセッションはないと報告されます。必要なものはアーカイブする*前に*取り出してください。アーカイブ済みのセッションが稼働中のものと取り違えられることは決してありません。また、同じ名前を再利用すれば本当に真っ新な状態から始まります。`start` がトランスクリプトをリセットするので、`send` のカーソルと `read` のオフセットは常に同じライフタイムを指します。

## 相手側のエージェントが終わったことをどう知るか

これが難しい部分です。rune は優先順位の順に3つの道具を用意しています。

**`--settle-ms N`（デフォルト 800）** — 子プロセスが N ミリ秒間静かになったら返ります。これが主要なシグナルです。settle の時計は、自分の入力が pty にエコーされたものではない出力が届いてから初めて動き始めます。そのため、プロンプトをエコーしてから考えて答えるエージェントでも、自分の言葉ではなく回答が返ってきます。

> **送信されないままのプロンプトも、見た目はまったく同じですが、原因は別のバグです。** rune は send のテキストを書き込み、そのキャリッジリターンは少し間を置いて*別の*書き込みとして送ります。両者をまとめて読む TUI は、リターンをテキストの一部として扱い、いつまでも送信しないからです。この遅延は、何も観測できないレースでした。Kimi 相手に計測したところ、以前の 0.05 秒では 3 回中 3 回とも送信に失敗しました。プロンプトはコンポーザに残ったまま、`send` はエコーだけを持って `settled: true` を返し、子プロセスはすでに書き込み済みのキー入力を待ち続けました。現在は 0.25 秒で、Claude Code、grok、Kimi のいずれも送信します。それよりさらに遅い TUI に出会った場合の見分け方は、`read --screen` で自分のテキストが入力ボックスに残ったまま見えることです。空文字列を送って裸のキャリッジリターンを届ければ、送信されます。

> **既知の制限、そして現在の rune で最も鋭い制限：入力を*再描画する*子プロセスは、その入力で settle してしまうことがあります。** 上記のルールが成り立つのは、エコーが一度だけ届く場合です。送信時に行を再描画するラインエディタは入力を二度目に送り、その二枚目のコピーが「子プロセスが発言した」と数えられてしまいます。`--settle-ms 800` で計測した結果、`irb` と `python3 -q` は 3 回中 3 回とも約 1 秒でエコーだけを持って `settled: true` を返し、本物の回答は数秒後に届いて*次の*呼び出しが拾うものに紛れ込みました。素の `bash -i` は影響を受けません。端末幅を超えて折り返す入力も同様です。
>
> **応答の中に、これと本物の回答を区別するものは何もありません。** `settled: true`、`busy_at_send: false` は同じですし、エコーは正しい応答の一部としても正当に現れます。修正されるまでは、再描画する REPL は影響を受けない `--wait-for-regex` で動かすか、応答に自分が送った内容以上のものが含まれるかを確認してください。

**`--wait-for-regex RE`** — 出力がマッチした時点で即座に返ります。決定的であり、相手が終了時に何を出力するか分かっているときには常に正解です。

```console
$ rune session send --name s --wait-for-regex '\$ $' "ls"
```

> **パターンのマッチ対象は応答であり、自分の入力のエコーではありません。** pty は書き込んだものをエコーするので、素朴な実装は自分の言葉が返ってきた瞬間に返ってしまいます。rune は*圧縮済み*テキストの中でエコーを特定します。両側からエスケープと空白を取り除いたもので、これこそが、送信した内容と、捕捉できたあらゆる変形エコーとの違いです。そして、再描画された入力のコピーが覆うマッチは拒否します。キーストロークごとに再描画する `python3 -q` の REPL 相手に計測したところ、以前は 4 回中 4 回とも、コードが実行される 8 秒も前の 0.22 秒で `matched: true` を返していました。現在は 3 回中 3 回、本物の出力を待ちます。
>
> 正直な主張は「*実際の子プロセスから捕捉できたエコーの形はすべて除外される*」であり、「*起こりえない*」ではありません。パターンが自分も送ったリテラルである場合、要求をそのまま引用して返す子プロセスには依然としてマッチされえます。また拒否にはコピーが*見える*ことが必要です。pty の読み取りがフレームを真っ二つに裂いた場合（フレームが再描画の途中で終わり、残りが次の読み取りで届く）、それはまだコピーとして認識できず、自分の入力の中にしか現れないパターンがその半分で満たされえます。トークンの直後でフレームを分割すれば、決定的に再現します。ですから、送信内容にも現れるパターンは、依然として避けるべき形です。

> **パターンのマッチ対象となる出力の量：エコーより後の直近 256 KB、読み取りのたびに 32768 文字さかのぼって再読します。** これは意図的な上限であり、2つの帰結があります。
>
> - **最大 32768 文字の単一のマッチは、ターンがどれほど大きくなっても必ず見つかります。** 各スキャンは前回停止位置のそこまで手前から再開するからです。待つに値するもの——マーカー、プロンプト、閉じフェンス——はすべてその範囲に十分収まります。
> - **32768 文字をまたがなければならない単一のマッチは、決して見つかりません。** 半メガバイトにまたがる `OPEN[\s\S]*CLOSE` は以前はマッチしましたが、今はしません。代わりにその send は `--settle-ms` か `--timeout-ms` まで走り続けます。`CLOSE` 単体で待ち、その間の範囲が必要なら `read` を使ってください。
>
> `\A` は依然としてウィンドウの先頭ではなく子プロセスの回答の先頭にアンカーされます。アンカー付きパターンが、ウィンドウがたまたま始まった位置で満たされることはありません。`^`、`$`、`\z` は影響を受けません。**応答はこのどれによっても制限されません。** `output` は依然として、そのターンで子プロセスが出力したすべてです。
>
> この上限があるからこそ、大きな回答にそもそも到達できます。以前はパターンが 4 KB 読み取りのたびにターン全体とマッチされていました。これはターンに対して二次であり、しかもスーパーバイザの唯一のスレッド上で行われるため、pty のドレインまで飢えさせていました。N MB を出力してからマーカーを表示する子プロセス相手に、そのマーカーと同じパターンで計測しました。
>
> | output | before | after |
> | --- | --- | --- |
> | 4 MB | 11.85s, matched | 0.53s, matched |
> | 12 MB | 90.51s, `timed_out: true`, 11.46 MB of 12.00 read | 0.98s, matched, 12.15 MB read |
> | 48 MB | 112.43s, matched | 3.37s, matched |
>
> 12 MB のケースでは、子プロセスがすでにマーカーを出力していた回答の 96% を握ったまま、send がタイムアウトを報告していました。

**`--timeout-ms N`（デフォルト 120000）** — 絶対的な上限です。期限切れでは、それまでに捕捉した分と `settled: false, timed_out: true` が返ります。失敗ではなく、ひとつの結果です。これは意図をもって設定してください。デフォルトが寛大なのはエージェントが遅いからで、呼び出しを間違えると2分の代償がかかります。

`--no-wait` は書き込んで即座に返ります。返答をまったく期待しないとき用です。その応答は別の形で、`{action, name, sent: true, waited: false}` です。何も待たなかったので、`output`、`cursor`、`prompt_detected` はありません。

`--no-newline` は、送信を意味する行末のキャリッジリターンなしにテキストを書き込みます。行を分割して組み立てたり、キーストロークを読む TUI を操作したりするとき用です。

### 応答のその他のフィールド

- `settled: true` — **待機がタイムアウトではなく応答で終わったことを示します。** これを立てる要因は3つあり、どれかは companion フィールドが教えます。settle ウィンドウの間、子プロセスが静かになった（companion フィールドなし）、`--wait-for-regex` がマッチした（`matched: true`）、子プロセスが終了した（`child_exited: true`）のいずれかです。これ単体では、子プロセスが静かになったことを意味し**ません**。正規表現マッチは静寂を一切伴わずにこれを立てます。60 秒の settle ウィンドウの 0.45 秒時点で `settled: true` を持つ応答がありえるのはこのためです。

  静寂を意味する場合*でも*、静寂には3つの原因があり、これでは区別できません。ターンが終わった、子プロセスが人間の入力を待っている、あるいは**子プロセスが長いコマンドをバックグラウンドに回して出力を止めた**。この3つ目が痛い目を見るケースです。ビジーマーカーの消失をポーリングしていた呼び出し元が、マーカーのないフレームを読んで作業完了と判断したら、実際の完了の 260 秒前でした。何かの*不在*をもって判断しようとしているなら、`settled` は単独では十分な根拠になりません。
- `timed_out: true` — `--timeout-ms` に先に到達しました。失敗ではなく、ひとつの結果です。
- `matched: true` — `--wait-for-regex` がマッチしました。
- `child_exited: true` — send の処理中に子プロセスが終了しました。
- `busy_at_send: true` — この send が届いた時点で子プロセスが*まだ出力を生成していた*ため、応答に前のターンの尻尾が含まれることがあります。回答が前の質問のものに見えるときは確認する価値があります。
- `regex_timed_out: true` — `--wait-for-regex` のパターンがマッチの予算を超えて放棄されました。ほぼ常に壊滅的なバックトラックを起こすパターンが原因です。単純化してください。
- `dropped_bytes` — ログがもはや保持していない過去の出力のバイト数です。ローテーションで消えたか、トランスクリプトの書き込み失敗で失われたかのどちらかです。これは `--since` カーソルを無効にし**ません**。カーソルは絶対的なままなので、ドロップ前のカーソルはエラーではなく、ドロップ*後*に保持されているすべてを返します。ドロップ領域の内部に落ちたカーソルは、その領域の後に続いた出力に解決されます。すでに配信済みの出力には決して解決されません。それが現在のターンの新しい出力のように見えて届いてしまうからです。
- `transcript_gap_bytes` — `status` と `send` の応答にのみ、かつどの書き込みにも記録できなかった出力がまだ未回収の間だけ現れます。ずれがディスク上にない唯一の時間窓です。次に成功した書き込みがそれを記録し、`read` は代わりに `dropped_bytes` として報告します。
- `screen_rows`、`screen_cols`、`screen_size_recorded` — `--screen` 付きの場合のみ。画面がレンダリングされたジオメトリと、それが子プロセスの記録された winsize かフォールバックか。詳しくは[子プロセスが実際に動いているサイズでレンダリングされる](#子プロセスが実際に動いているサイズでレンダリングされる)を参照してください。

### `child_busy` と `idle_ms` は `send` ではなく `read` のフィールドです

子プロセスが settle ウィンドウ内に何か出力したかどうか、そして最後に出力してからどれくらい経ったか。これは「まだ動いているのか」の構造化された形です。相手側の UI を grep してビジーマーカーを探す代わりに、こちらを使ってください。UI は見せ方の問題であり、予告なく変わります。

**これらは `read` と `list` のフィールドであり、`send` の応答のフィールドではありません。** `send` は子プロセスが settle するまでブロック済みなので、終わってから尋ねてください。

```console
$ rune session send --name grok --settle-ms 2500 "run the suite"
$ rune session read --name grok --tail 1 --json     # child_busy, idle_ms
```

この文書は以前、両方を `send` の応答のフィールドとして記載していました。これは最も困る形で間違っています。`send` の応答から `.child_busy` を読んだ呼び出し元は `nil` を受け取り、UI の grep に退避してしまいます。それこそ、これらのフィールドが置き換えるために存在するものそのものです。

名前が示すのは子プロセスが*出力中*であることであって、*作業中*であることではない点に注意してください。コマンドをバックグラウンドに回して静かになった子プロセスは `child_busy: false` を報告します。

### 長いトランスクリプトの中から見つけ出す

`--since` と `--tail` は、欲しいものが途中にあるときには役に立ちません。エージェントを動かした一日の作業は 379KB に達しました。

```console
$ rune session read --name grok --grep 'THE BOARD' --context 2
```

マッチの対象は生のストリームではなく*クリーニング済み*のテキストです。フルスクリーンのエージェントの再描画フレームは、単語をエスケープシーケンスのまたぎで分割するからです。画面にはっきり見えるパターンが、バイト列にはマッチしません。応答には `grep_matches` が載ります。

**クリーニング済みはレンダリング済みではありません。この違いが刺さるのは、まさにセッションが駆動するために存在する種類の子プロセスです。** クリーニング済みテキストは、エスケープを取り除いた再描画ストリーム全体です。つまり、上書きされた履歴もマッチし、画面がとうに表示しなくなった行が、クリーンな独立した1行として返ってきます。カーソルで描画されたフレームには改行が一切ないので、それは1つの grep 行であり、`--context` は何もせず、1回のマッチでフレーム全体が、もっともらしい見た目の `grep_matches: 1` とともに返ります。そして、画面上に見えるものにアンカーしたパターンは `grep_matches: 0` を返しえます。画面上の隣接はストリーム上の隣接ではないからです。問いが「*今、何が表示されているか*」であるなら `--screen` を使ってください。`--grep` は長いトランスクリプトの中から1行を見つけるためのもので、それが得意な仕事です。

コンパイルできないパターンは例外ではなく `grep_error` として返り、そして**何も選択しません**。`output` と `clean_output` は空で、`grep_matches` は存在しません。これが「フィルタが一度も走らなかった」と「フィルタが何も見つけなかった」を区別する方法です。read 自体は成功するので、`cursor`、`prompt_detected`、`child_busy` はすべてそのまま残っています。どれもパターンに依存しませんし、前に進むにはカーソルが必要です。（`send --wait-for-regex` は別です。あちらはパターンがいつ返るかを決めるので、不正なものは即座に拒否されます。）

### `prompt_detected` は参考情報にすぎません

すべての `send`/`read` の結果には `prompt_detected` が載りますが、**これを条件分岐の根拠にしないでください**。そして、どちら側に外れるかを知っておいてください。

実際の出力相手に計測した結果、プレーンテキストでは `false`、裸の `$ ` では `false`、**`Do you want to proceed?` では `false`**、`❯ ` では `true` です。つまり grok 相手では実質的にすべての read で `true` になります。grok のコンポーザは常に `❯` で終わるからです。ある呼び出し元は 8 回中 8 回 `true` を見て、何も区別していないと結論づけました。区別はしています。ただ、検出しているのが「*プロンプトらしい形の最終行*」であり、「これは自分の入力待ちか」とは別の問いなのです。上記の3つ目のケースに注意してください。最も捕捉してほしい許可ダイアログで、まさに `false` になります。それについては画面を見てください。rune のプロンプトパターンはシェルらしい形のプロンプト（`user@host:~$`、`[y/N]`、`Password:`）にマッチし、意図的に保守的です。エージェントの REPL はたいていそのどれにも似ていないので、まさに駆動したい CLI に対しては、通常は `false` になります。プロンプトを待つ設計にすれば、実際のターゲットのほとんどでハングします。だからこそ settle 時間が主要なシグナルなのです。

## トランスクリプトを読む

`read` はセッションの永続トランスクリプトを再生します。セッションが稼働中でも、すでに停止していても、同じように動作します。

```console
$ rune session read --name grok --tail 50
$ rune session read --name grok --since 41234     # page from a cursor a previous call returned
```

すべてのセッションは、`rune watch` が生成するのと同じ形式の NDJSON イベントログを書き込みます。そのため、別のペインから稼働中のセッションを追いかけられます。

```console
$ tail -f ~/.rune/projects/<project>/sessions/grok/output.ndjson
```

フルスクリーンの TUI エージェントは大量の ANSI 再描画トラフィックを生成するので、トランスクリプト全体を読むより `--tail` や `--max-output` を優先してください。

`--max-output=BYTES` は先頭部分と末尾部分を残し、継ぎ目をテキストそのものの中に示します。

```
...the last line before the cut
[rune] ==== 41233 bytes omitted by --max-output ====
the first line after it...
```

この行がなければ、応答は子プロセスが出力したことのない連続した出力のように読めてしまいます。計測では、`--max-output=200` を指定した 201 バイトのトランスクリプトで、たった 1 バイトが落ちたことで `chsh -s /bin/zsh` が `chsh -s bin/zsh` になりました。別の、しかも依然もっともらしいパスです。このマーカーはトランスクリプトではなく rune の注釈なので、BYTES の計上対象ではなく、応答は予算を少し超えることがあります。`truncated` と `omitted_bytes` が依然として権威ある答えです。子プロセスはマーカーに似た行を含め、何でも出力しうるからです。

### `--screen`：届いたものではなく、端末が表示しているもの

フルスクリーンのエージェント相手では、通常これが欲しいフィールドです。バイトストリームにはすべての再描画のすべてのフレームが含まれ、回答はその間に分割されています。画面には、表示されているものだけが含まれます。

```console
$ rune session send --name grok --screen -- "reply with just the branch name"
$ rune session read --name grok --screen
```

grok 相手に計測した結果、361KB のトランスクリプトは 1.1KB の画面にレンダリングされ、エージェントが明らかに表示していた回答は、**3 ターン中 3 回ともバイトストリームには存在せず、3 ターン中 3 回ともレンダリングされた画面には存在しました**。内容でマッチさせるなら、`screen` に対してマッチさせてください。

これが*でない*ものが3つあります。これは*最終状態*なので、スクロールアウトしたものは失われています。何が起きたかの記録はトランスクリプトの役目です。opt-in なのは、画面を描画する子プロセスに対してのみ意味があるからです。cooked モードのシェルでは、バイトストリームがすでにそのまま回答です。そして、これは**read のフィルタでは制限されません**。`--since`、`--tail`、`--grep`、`--max-output` はすべて `output`/`clean_output` を制限し、`screen` には触れません。制限はありますが、ジオメトリによるものです。最大で `screen_rows x (screen_cols + 1)` で、どちらも同じ応答で返ります。219,941 バイトのトランスクリプトは約 2KB にレンダリングされます。つまり `--max-output=200 --screen` は、あなたが指定していない規則で制限された、制限付きの応答を返します。

### 子プロセスが実際に動いているサイズでレンダリングされる

セッションの子プロセスは 40x120 で起動し、`attach` がそれを引き継いだ端末のサイズにリサイズします。つまりサイズは定数ではなく、固定サイズでレンダリングすると、誰も見たことのない画面ができあがります。スーパーバイザは子プロセスの winsize を変更するたびに現在の値を `meta.json` に記録し、`--screen` はそのサイズでレンダリングして、それを報告します。

```console
$ rune session read --name grok --screen --json | jq '{screen_rows, screen_cols, screen_size_recorded}'
{ "screen_rows": 30, "screen_cols": 100, "screen_size_recorded": true }
```

pyte 0.8.2 と GNU screen 4.00.03 を独立したオラクルとして同じバイト列を再生させ（両者はすべての形状で完全に一致しました）、端から端まで計測しました。

| 駆動した内容 | 不一致行数（修正前） | 不一致行数（修正後） |
|---|---|---|
| コントロールソケット経由で 30x100 にリサイズ、子プロセスは WINCH で再描画 | 36/37 | **0/31** |
| 同様に 24x80 | 30/31 | **0/25** |
| 同様に 12x40 | 18/19 | **0/13** |
| 同様に 50x200 | 50/51 | **0/51** |
| 同様に 40x120（サイズが一致） | 0/41 | 0/41 |
| 30x100 の pty から実際に `rune session attach`、子プロセスは WINCH を無視 | 29/30 | **0/30** |

attach の行では、オラクルにはその端末自身が受け取ったバイト列が与えられています。つまり「30 中 0」は、rune のレンダリングした画面が、人間が見ていたものと行単位で一致したことを意味します。

**実際のジオメトリとフォールバックを区別するのは `screen_size_recorded` であり、数値ではありません。** 40 行の端末から attach されたセッションは、フォールバックとまったく同じ 40x120 を記録するので、数値の組だけでは区別を伝えられません。`screen_size_recorded` が true になるのは、報告されたサイズが `meta.json` に実際に保持されていたものである場合だけです。false になるのは3つのケースで、すべて 40x120 を報告します。

- 誰もリサイズしていないセッション。スーパーバイザは pty を 40x120 に設定しますが記録はしません。つまりこの場合のフォールバックは推測ではなく、子プロセスが実際に動いているサイズです。
- rune がサイズを記録するようになる前に書かれたセッションディレクトリ。
- 端末として使えない記録済みサイズ。破棄またはクランプされ、アロケートはされません。`meta.json` はディスク上のファイルであり、グリッドは即座に構築されるからです。

コントロールソケット経由で届くリサイズは 300x1000 にクランプされます。実在のどの端末よりも大きい値です。クランプは記録だけでなく pty にも適用されるので、子プロセス、記録、レンダリングは常に一致します。pty の winsize フィールドは 16 ビットであり、65535x65535 が記録されると、以後すべての `--screen` がそのサイズのグリッドを駆動することになります。意図的に敵対的な 683KB のトランスクリプトでは、`read --screen` 1 回のコストは 40x120 で 0.76 秒、クランプ上限で 3.41 秒、クランプなしで 17.72 秒でした。

**未解決のリサイズのケースが1つあります。** 保持されているトランスクリプト全体は子プロセスの*現在の*サイズでレンダリングされます。そのため、ジオメトリが途中で変わった場合、変更前に描画された出力は新しいサイズで再フローされます。フルスクリーンのエージェントではこれが正しく、証明可能です。TUI は SIGWINCH で再描画しますし、attach 時にスーパーバイザはバックログを端末のサイズで端末にリプレイします。トランスクリプト全体をそのサイズでレンダリングすることは、まさにそれを再現します。上記の 30 中 0 の attach の行は、SIGWINCH を完全に無視する子プロセスに対しても成立します。未解決なのは、一度描画して二度と再描画せず、*かつ*すでにアタッチされている端末の下で pty がリサイズされる子プロセスです。その端末はすでに描画済みのグリフを再フローしており、照合すべき基準となる答えが存在しないからです。そのようなストリームを 40x120 から 24x80 に途中で縮小した場合、GNU screen はカーソル行だけを残し、pyte は何も残さず、両者は残したわずかな内容の1行について互いに不一致でした。rune は内容を保持して再フローするので、両者とも異なります。古い固定サイズでのレンダリングは、生の行数ではこちらで良い成績でした（24 に対して 15 行の不一致）。しかしそれは、ほぼ空白の画面がたまたまほぼ空白のオラクルと一致したからであって、誰かにより正しいものを見せたからではありません。

**レンダリングは直近 512KB から行われ、エージェントによっては目に見える代償があります。** grok の出力 4.5MB の調査では、絶対カーソル移動が 109,364 回、同期更新ブラケットが 31,798 回、そして消去が**ゼロ**でした。`\e[K` も `\e[2K` も `\e[2J` も、スクロール領域もありません。位置決めと上書きだけで再描画するエージェントは、どれほど昔に書いたセルでも端末がすべて覚えていることに依存しています。ウィンドウからのレンダリングは代わりに真っ白なグリッドから始まるので、一度描画されて二度と再描画されなかったもの——ヘッダ、バナー——は単純に存在せず、rune はそれが欠けていることを検出できません。`--screen` を頻繁に読んでも助けにはなりません。ウィンドウは時間ではなくバイト数で測られるからです。

同じ調査は、より微妙な点も説明します。エージェントが消去を一切しない場合、画面上の重複した行は完全に忠実な表示かもしれません。レイアウトが1行下にずれて新しい位置に再描画された場合、古いコピーを消すものが何もなく、**実際の端末でもその重複が表示されます**。繰り返された行を rune のバグとして扱う前に、そのエージェントが何か消去しているかどうかを確認してください。

### 既知の制限：ポーリングした `--screen` が描画途中のフレームを返すことがあります

実際の使用から報告されたもので、**未修正**です。再描画中のエージェントに対して `--screen` をポーリングすると、再描画の途中のフレームが返ることがあります。報告されたケースでは、1行が隣接する2行に重複していました。

2つの修正案が計測され、却下されました。連続するレンダリングを比較して繰り返し現れたものだけを返す方式は、何もしないより**悪い**結果でした。20 回中 13 回の破損フレームに対し、何もしなければ 11 回です。周期的に描画するエージェントは同じフレームを二度レンダリングすることが稀なので、このチェックはタイムアウトして、結局破損フレームをそのまま渡してしまいます。安定性を静寂として再定義する方式は、破損を再現することさえできませんでした。同一の子プロセスで 11/20 が1回、0/20 が2回という結果は、ハーネスが見かけ上のものを計測していなかったことを意味します。「完了に見える」方向に静かに失敗する修正は、計画の立てようがある制限よりも悪いのです。

**どう対処するか。** 1枚のレンダリング済みフレームを、取り消せない判断の根拠にしないでください。値を読むなら、2回ポーリングして一致を要求してください。マーカーを待つなら、`--screen` がスナップショットであるのに対し、`--wait-for-regex` は決定的です。

**rune の落ち度ではないかもしれません。** あるエージェントの出力 4.5MB の調査では、消去が一切ゼロでした。消去をせずにレイアウトをずらすエージェントは、古いコピーを画面に残します。実際の端末でもその重複は表示されます。rune のレンダラは、この調査から構築した6つのプロファイル全体で、独立したエミュレータと一致します。重複行を rune のバグとして報告する前に、そのエージェントが何か消去しているかどうかを確認してください。

### トランスクリプトには上限があります

ファイルとスーパーバイザのメモリの両方に上限があるので、一日中動かし続けたセッションが際限なく肥大化することはありません。ファイルの上限は2重に強制されます。通常はローテーションによって、そしてローテーションがまったく成功できない場合（ディレクトリが書き込み不可になった、ディスクが満杯のまま、など）は上限の2倍のハードリミットによって。それを超えた出力は、書き込まれるのではなくドロップとして記録されます。どちらの場合も `read` は `dropped_bytes` を報告し、カーソルは絶対的なままです。ローテーションが古い出力を落とした場合も、`read` は `dropped_bytes` を報告し、カーソルは絶対的なままです。カーソルはストリーム内の同じ位置を指し続けますが、その位置の出力はもう保持されていないだけです。

失敗したトランスクリプト書き込み（ディスク満杯、書き込み不可のディレクトリ）も同じように出力を落とします。ただし、その後も続くストリームの*途中*での話です。それらのバイトは保持され、書き込みが再開され次第記録されます。カーソルは累計の合計を飛び越えるのではなく、各ドロップ領域を通過するようマッピングされるので、穴の前の出力が新しいもののように再配信されることはありません。書き込みが成功するまでは、ディスク上にその穴を記録する場所がありません。`status` の `transcript_gap_bytes` が報告するのは、まさにそれです。

## 実際のエージェントを駆動する前に知っておくべきこと

- **`start` が返るのは、子プロセスではなく*スーパーバイザ*の準備ができたときです。** エージェント CLI の起動には数秒かかり、リッスンを開始する前に送られた入力は単純に失われます。起動したてのセッションを駆動する前に、準備完了のマーカーを待ってください。`read` をポーリングするか、最初の `send` を `--wait-for-regex` にします。
- **settle はヒューリスティックです。** 回答の途中で `--settle-ms` より長く止まる子プロセスは、途中で切れた応答を返します。値を上げるか、`--wait-for-regex` を使ってください。
- **`--wait-for-regex` が見るのは直近 256 KB であり、ターン全体ではありません。** 最長 32768 文字の単一のマッチは必ず見つかります。それをまたがなければならないマッチは決して見つかりません。メガバイトを挟むパターンではなく、マーカーを待ってください。
- **1024 バイト以上の1行は、cooked モードの子プロセスの中に消えます。** これは `MAX_CANON`、端末の制限であって rune のものではありません。ライン規則はそれより長いカノニカル行を組み立てられず、黙って捨てます。1023 バイトは届き、1024 バイトは届きません。ほとんどのエージェント CLI は端末を raw モードで動かすので影響を受けません（300KB がバイト単位で完璧に届きます）。対話シェルも同様です。`bash --norc -i` は readline を使い、端末は raw モードになり、1995 文字の行をバイト単位で完璧に受け取ります。この制限が刺さるのは *cooked* モードで読む子プロセスです。素の `cat` や、readline なしで stdin を読むスクリプトです。分割するか、raw モードのターゲットを駆動してください。
- Enter はキャリッジリターンとして送信されます。実際の端末が送るものと同じなので、raw モードの TUI はそれを受け取ります。cooked モードのシェルには影響しません。
- 子プロセスの pty には明示的なウィンドウサイズが与えられます。デタッチされたセッションにはコピー元の端末がなく、未設定の pty は 0x0 になるためです。これではフルスクリーンのエージェントは虚空にレンダリングすることになります。起動時は 40x120 で、アタッチされている端末がある間はそれに追従し（上限 300x1000）、最後の端末が離れると 40x120 に戻ります。`--screen` はその時点で現在のサイズでレンダリングします。

## 状態の置き場所

`RUNE_HOME`（デフォルト `~/.rune`）に、所有者のみのパーミッションで配置されます。

```
$RUNE_HOME/projects/<project>/
  sessions/<name>/
    meta.json        0600   pid, supervisor pid, command, state, child terminal size
    output.ndjson    0600   full transcript
    supervisor.log   0600   supervisor stderr, for when something goes wrong
    control.sock     0600   the supervisor's control socket
  archive/<stamp>-<name>/   archived sessions, out of the live namespace
```

セッションを隔離したい場合（テスト、サンドボックス、並行作業）は `RUNE_HOME` を設定してください。

`meta.json` は rename による置き換えであり、インプレースで切り詰められることはありません。他のすべての rune プロセスが、ロックを取らずに「このセッションは存在するか、生きているか」を答えるためにこれを読むからです。短くなっている時間窓は、`send` が「No such session」と答え、`list` が `state: dead` を報告する時間窓でした。子プロセスの winsize を記録するようになったことで、書き込みはリサイズごとに発生するようになり、人間がウィンドウの端をドラッグすればフレームごとに1回発生します。実際の attach を 7.5 秒かけて 250 のウィンドウ形状にドラッグし、別プロセスに meta をタイトループで読ませて計測しました。修正前は 294,728 回中 90 回の読み取りが読めずに返り、修正後は 312,582 回中 0 回でした。

## 多数を同時に動かすコスト

1セッションにつき1つのスーパーバイザプロセスです。この隔離は意図的です。固まったエージェントは自分のセッションだけを道連れにし、他には影響しません。その代償はセッションごとの Ruby インタプリタであり、ファンアウトする前に知っておく価値があります。

アイドル状態の子プロセスでの計測結果：

| セッション数 | 常駐メモリ | ディスクリプタ |
|----------|-----------------|-------------|
| 24 | 543 MB | 648 |
| 60 | 1361 MB | 1620 |

つまり**1セッションあたり約 23 MB と 27 ディスクリプタ**で、一定です。60 でも 24 でも同じで、send のラウンドを重ねても変わりません。コストは驚くようなものではなく、予測可能で線形です。ただし前払いです。60 のエージェントは、どれかが何かをする前から、1 ギガバイト以上を消費します。

並行実行そのものも同じテストで持ちこたえました。60 の同時 `start` はすべて成功し、すべての send は宛てられたセッションに届き、`list` は現実と一致し、後に残って動いているものはありませんでした。同じツールに対して `--name` *なし*で 30 の同時 `start` を呼ぶと、30 の異なるコードネームが生成され、衝突はありませんでした。

## スコープ

rune はセッションの**ブローカ**であり、メッセージバスではありません。セッションを保持し、名前で宛先を指定します。誰が誰と話すかを決めるのは、呼び出し側のエージェントの仕事です。名前はすでに持っているのですから。セッション間ルーティング、エージェントごとのプロファイル、共有会話ログは、意図的にスコープ外です。
