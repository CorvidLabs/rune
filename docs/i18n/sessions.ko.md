# 지속 세션 (`rune session`)

`rune run`은 명령을 띄운 뒤 출력을 모두 버퍼에 담고 한 번만 반환합니다. `rune watch`는 세션을 실시간으로 스트리밍하지만 stdin에 실제 사람용 터미널이 있어야 합니다. 둘 다 서로 다른 `rune` 호출에 걸쳐 REPL 형태의 자식 프로세스를 열어 둘 수 없습니다 — 그래서 에이전트는 *`codex`를 시작하고, 프롬프트를 보내고, 답을 기다린 다음, 후속 질문을 보내는* 방법이 없었습니다.

`rune session`이 바로 그 기능을 더합니다. 이름이 있는 세션의 자식 프로세스는 그것을 시작한 `rune` 호출보다 오래 살고, `send`는 자식이 실제로 답을 할 때까지 블록합니다.

## 이름 붙이기: 모든 세션에는 이름이 있고, 직접 고를 일은 거의 없습니다

세션은 **디렉터리**마다 네임스페이스가 나뉩니다: 프로젝트는 작업 디렉터리의 basename에 그 경로의 해시를 더한 값이므로, 같은 저장소의 git worktree 두 개는 서로 다른 두 네임스페이스가 됩니다. `start`는 자신이 등록한 네임스페이스를 알려 주고, 그 필드를 읽는 것이 5분짜리 우회와 한 시간의 차이를 만듭니다:

```console
$ rune session start --name reviewer -- grok
{"name":"reviewer","project":"myrepo-0a922f34","command":["grok"],"state":"running",...}
```

잘못된 디렉터리에서 `read`하면 *"No such session"*이라고 답하고, 그 오류가 떠올리게 하는 `list`는 빈 배열을 보여 줍니다 — 이는 세션이 죽었다는 확인처럼 읽히지, 지금 다른 곳에 서 있다는 뜻으로는 읽히지 않습니다.

```console
$ rune session start -- grok
{"name":"grok-amber","command":["grok"],"child_pid":68012,"supervisor_pid":67926,"state":"running"}
```

`--name`을 생략하면 rune이 아직 쓰이지 않은 `<tool>-<word>` 코드명을 생성합니다. 생각보다 중요합니다: 세션이 둘이 되는 순간 "the grok session"은 더 이상 아무것도 의미하지 않고, 세션을 띄우는 에이전트가 식별자를 직접 만들어 내서는 안 됩니다. 직접 고르고 싶을 때는 `--name reviewer`를 넘기세요.

이름은 **프로젝트 범위**로 한정됩니다 — 감싸고 있는 git working tree, 또는 git 밖이면 그 디렉터리 자체입니다. 한 checkout의 `reviewer`와 다른 checkout의 `reviewer`는 서로 다른 세션이고, 잘못된 디렉터리에서는 어느 쪽에도 닿을 수 없습니다:

```console
$ rune session list                  # this project only
$ rune session list --all-projects   # everything, labelled by project
```

## 루프

```console
$ rune session start --name grok -- grok
{"name":"grok","command":["grok"],"child_pid":68012,"supervisor_pid":67926,"state":"running"}
```

**`start`가 성공했다고 해서 자식 프로세스가 돌아가고 있는 것은 아닙니다.** 명령이 존재하지 않아도 응답은 여전히 `status: "ok"`이고 `rune`은 여전히 종료 코드 0으로 끝납니다 — 본문에는 `state: "exited"`와 `exit_code: 127`이 들어 있습니다. `start` 자체는 된 것이고, 자식이 즉시 죽은 것입니다. 프로세스 종료 상태가 아니라 `state`를 확인하세요.

`start`는 즉시 반환하고 `rune` 프로세스는 종료됩니다. `grok`는 계속 돌아가며, pty를 붙잡고 있는 분리된 supervisor가 소유합니다.

```console
$ rune session send --name grok --settle-ms 2500 "reply with exactly the word PONG"
```

`send`는 프롬프트를 쓰고, grok가 2.5초 동안 출력을 내지 않을 때까지 기다린 다음, **그 send가 만들어 낸 것만** 반환합니다. 호출 사이에 상태가 유지되는 이유는 매번 같은 자식 프로세스이기 때문입니다:

잘못 적은 플래그는 자식에게 입력으로 넘어가지 않고 거부됩니다. `send --name grok --settle_ms 500 'echo HELLO'`(밑줄이지, 하이픈이 아님)는 예전에는 어떤 플래그에도 맞지 않아서, 플래그와 그 값과 프롬프트가 한 줄로 이어져 에이전트에 쓰였습니다 — `status: ok`였고, 유료 모델이 `--settle_ms 500 echo HELLO`에 답했습니다. 검사는 첫 번째 피연산자 앞과 `--` 앞의 토큰만 보므로, `start --name x claude --resume`은 여전히 에이전트를 그 자신의 플래그와 함께 시작하고, `send --name x -- --settle_ms`는 여전히 `--settle_ms`를 글자 그대로 입력합니다.

```console
$ rune session send --name s --settle-ms 300 "MEMORY=persisted"
$ rune session send --name s --settle-ms 300 'echo "value=$MEMORY"'
value=persisted
```

```console
$ rune session list
● grok-amber  running  idle 3s   grok
    Thought for 1s
● worker      running  idle 2m   bash --norc -i
    bash-3.2$

$ rune session stop --name grok-amber
```

각 행에는 세션이 얼마나 조용했는가와 마지막으로 출력한 줄이 들어 있습니다 — 에이전트가 여러 개 동시에 돌아가고 있을 때 *"이게 동작 중인지 멈춘 건지, 지금 뭘 하는 건지"*에 대한 가장 빠른 답이 됩니다. 같은 필드(`idle_ms`, `last_line`)는 `--json`에도 있습니다.

## 운전대를 잡고, 다시 돌려주기

```console
$ rune session attach --name grok-amber
[rune session] attached — Ctrl-] to detach (session keeps running)
```

`attach`는 실제 터미널을 실행 중인 세션에 연결합니다: 출력은 화면에 스트리밍되고, 키 입력은 에이전트로 가며, 연결 시 현재 화면이 다시 재생되어 빈 화면만 보게 되지 않습니다. 그리고 **자식은 터미널 크기에 맞춰 리사이즈되고**(창 크기를 바꾸면 따라갑니다) 전체 화면 에이전트가 헤드리스 기본값이 아니라 내 창에 맞춰 배치됩니다. detach하면 자식은 그 기본값으로 돌아가므로, 프로그램으로 보내는 `send`는 attach 여부와 관계없이 같게 렌더링됩니다. **Ctrl-]**는 detach하고 모든 것을 그대로 돌려 둡니다 — 이것이 자신이 띄운 자식을 소유하는 `rune watch`와의 차이 전부입니다. Ctrl-C는 일부러 detach 키가 *아닙니다*: 폭주하는 에이전트를 중단할 수 있도록 자식에게 계속 전달되어야 하기 때문입니다.

## 아카이브

중지된 세션은 이름을 계속 예약해 두고 `list`를 지저분하게 만듭니다. 아카이브하세요:

```console
$ rune session stop --name reviewer
$ rune session archive --name reviewer
$ rune session list --archived
```

아카이브하면 이름이 해제되고, 트랜스크립트는 프로젝트의 아카이브 아래로 들어갑니다. 아카이브된 세션은 `read`의 밖에 있습니다 — `read --name`을 하면 no such session이라고 알려 주므로, 아직 필요한 것은 아카이브하기 *전에* 꺼내 두세요. 아카이브된 세션은 살아있는 세션으로 오인될 수 없고, 이름을 다시 쓰면 정말로 처음부터 시작합니다 — `start`가 트랜스크립트를 초기화하므로 `send` 커서와 `read` 오프셋은 항상 같은 수명을 가리킵니다.

## 상대 에이전트가 끝났는지 아는 법

이게 어려운 부분이고, rune은 선호 순서대로 도구 세 가지를 줍니다.

**`--settle-ms N`(기본값 800)** — 자식이 N ms 동안 조용해지면 반환합니다. 이게 기본 신호입니다. settle 시계는 pty가 내 입력을 에코한 것이 아닌 출력이 도착한 뒤에야 시작되므로, 프롬프트를 에코한 다음 생각하고 답하는 에이전트는 내 말이 아니라 답을 돌려줍니다.

> **제출되지 않는 프롬프트도 똑같이 보이며, 다른 버그입니다.** rune은 send의 텍스트를 쓴 다음 잠시 뒤에 캐리지 리턴을 별도 write로 보내는데, 둘을 한꺼번에 읽는 TUI는 리턴을 텍스트의 일부로 보고 제출하지 않기 때문입니다. 그 지연은 아무도 관찰할 수 없는 레이스입니다: Kimi를 상대로 측정했을 때, 예전 0.05s는 send 3건을 3건 모두 놓쳤습니다 — 프롬프트는 composer에 앉아 있고, send는 에코만 담은 채 `settled: true`를 반환했으며, 자식은 이미 쓰인 키 입력을 기다리고 있었습니다. 지금은 0.25s이고, Claude Code와 grok와 Kimi는 모두 제출합니다. 더 느린 TUI를 만나면, 단서는 `read --screen`이 입력 상자에 텍스트가 앉아 있는 것을 보여 준다는 점입니다: 빈 문자열을 send하면 캐리지 리턴만 전달되고, 그러면 넘어갑니다.

> **알려진 한계이고, 지금 rune에서 가장 날카로운 것입니다: 입력을 다시 그리는 자식은 그 입력에서 settle할 수 있습니다.** 위의 규칙은 에코가 한 번만 올 때 성립합니다. 제출 시 줄을 다시 그리는 라인 에디터는 입력을 두 번째로 보내고, 그 두 번째 복사본은 자식이 말한 것으로 칩니다. `--settle-ms 800`으로 측정하면, `irb`와 `python3 -q`는 에코만 담은 채 약 1초 만에 `settled: true`를 반환합니다 — 각각 3번 중 3번입니다. 실제 답은 몇 초 뒤에 도착해 다음 호출이 잡는 쪽에 떨어집니다. 평범한 `bash -i`는 영향을 받지 않으며, 터미널 너비를 넘어 줄바꿈되는 입력도 마찬가지입니다.
>
> **응답 안에서는 이것을 진짜 답과 구별할 수 없습니다** — `settled: true`, `busy_at_send: false`이고, 에코도 올바른 응답의 정당한 일부입니다. 고쳐지기 전까지는 다시 그리는 REPL을 `--wait-for-regex`로 다루세요, 이쪽은 영향을 받지 않습니다. 또는 응답에 보낸 것 이상의 내용이 들어 있는지 확인하세요.

**`--wait-for-regex RE`** — 출력이 일치하는 즉시 반환합니다. 결정적이고, 상대가 끝났을 때 무엇을 출력하는지 알 때는 맞는 선택입니다:

```console
$ rune session send --name s --wait-for-regex '\$ $' "ls"
```

> **패턴은 응답에 맞추지, 입력의 에코에 맞추지 않습니다.** pty는 쓴 내용을 에코하므로, 순진한 구현은 내 말이 돌아오는 순간에 반환합니다. rune은 *압축된* 텍스트에서 에코를 찾습니다 — 양쪽에서 이스케이프와 공백을 제거한 것이며, 이것이 보낸 것과 우리가 잡을 수 있었던 모든 변형된 에코의 차이입니다 — 그리고 다시 그려진 입력 복사본이 덮는 일치는 거부합니다. 키 입력마다 REPL을 다시 그리는 `python3 -q`를 상대로 측정하면, 예전에는 `matched: true`로 0.22s 만에 반환했고, 코드가 실행되기 8초 전이었습니다, 4번 중 4번이었습니다; 지금은 실제 출력을 기다리며, 3번 중 3번입니다.
>
> 정직한 주장은, 실제 자식에서 잡을 수 있었던 *모든* 에코 형태는 제외된다는 것이지, *일어날 수 없다*는 것이 아닙니다. 패턴이 보낸 리터럴이기도 하면, 요청을 그대로 인용해 돌려주는 자식은 여전히 그 패턴을 충족할 수 있습니다. veto가 복사본을 보려면 복사본이 *보여야* 합니다: pty read가 반으로 찢은 다시 그리기는 — 프레임이 다시 그리기 중간에 끝나고 나머지가 다음 read에 도착하면 — 아직 복사본으로 알아볼 수 없고, 내 입력 안에만 나타나는 패턴은 그 절반으로 충족될 수 있습니다. 토큰 직후에서 프레임을 나누면 결정적으로 재현됩니다. 따라서 보낸 내용에도 나타나는 패턴은 여전히 피해야 할 형태입니다.

> **패턴을 맞추는 출력의 양: 에코 이후 가장 최근 256 KB이며, 매 read마다 32768자를 되돌아가 다시 읽습니다.** 의도된 한계이고 결과는 두 가지입니다.
>
> - **32768자까지의 단일 일치는, 턴이 아무리 커져도 항상 찾습니다.** 각 스캔이 이전 스캔이 멈춘 지점보다 그만큼 뒤에서 다시 시작하기 때문입니다. 합리적으로 기다릴 만한 것 — 마커, 프롬프트, 닫는 fence — 는 그보다 훨씬 안쪽에 있습니다.
> - **32768자를 넘어야 하는 단일 일치는 절대 찾지 않습니다.** 반 메가바이트에 걸친 `OPEN[\s\S]*CLOSE`는 예전에는 맞았고 지금은 맞지 않습니다; send는 대신 `--settle-ms` 또는 `--timeout-ms`까지 계속 갑니다. `CLOSE`만 따로 기다리고, 그 사이를 봐야 하면 `read`를 쓰세요.
>
> `\A`는 여전히 윈도우의 시작이 아니라 자식 답의 시작에 고정됩니다 — 고정된 패턴은 윈도우가 어디서 시작하든 그것으로 충족되지 않습니다. `^`, `$`, `\z`는 영향을 받지 않습니다. **응답은 이것으로 잘리지 않습니다:** `output`은 여전히 그 턴에 자식이 만든 전부입니다.
>
> 그 한계 덕분에 큰 답에 아예 닿을 수 있습니다. 예전에는 매 4 KB read마다 턴 전체에 패턴을 맞춰서, 턴 크기에 대해 이차였습니다 — 게다가 supervisor의 유일한 스레드에서 돌아서 pty drain도 굶겼습니다. N MB를 내보낸 뒤 마커를 출력하는 자식을 상대로, 그 마커를 패턴으로 삼아 측정하면:
>
> | 출력 | 이전 | 이후 |
> | --- | --- | --- |
> | 4 MB | 11.85s, matched | 0.53s, matched |
> | 12 MB | 90.51s, `timed_out: true`, 12.00 MB 중 11.46 MB 읽음 | 0.98s, matched, 12.15 MB 읽음 |
> | 48 MB | 112.43s, matched | 3.37s, matched |
>
> 12 MB에서 send는 타임아웃을 보고하면서, 자식이 이미 마커를 출력한 답의 96%를 들고 있었습니다.

**`--timeout-ms N`(기본값 120000)** — 하드 캡입니다. 만료되면 잡은 것에 `settled: false, timed_out: true`가 붙습니다 — 실패가 아니라 결과입니다. 일부러 설정하세요: 기본값이 넉넉한 이유는 에이전트가 느리기 때문이고, 그래서 잘못된 호출은 2분이 듭니다.

`--no-wait`는 쓰고 즉시 반환합니다, 답을 전혀 기대하지 않을 때입니다. 응답 형태가 다릅니다 — `{action, name, sent: true, waited: false}`이고, `output`, `cursor`, `prompt_detected`는 없습니다, 기다린 것이 없기 때문입니다.

`--no-newline`은 제출하는 끝 캐리지 리턴 없이 텍스트를 씁니다, 줄을 조각으로 조합하거나 키 입력을 읽는 TUI를 다룰 때입니다.

### 응답의 다른 필드들

- `settled: true` — **타임아웃이 아니라 대기가 응답된 것입니다.** 세 가지가 이것을 켜고, 짝 필드가 어느 쪽인지 알려 줍니다: 자식이 settle 창 동안 조용해진 경우(짝 필드 없음), `--wait-for-regex`가 맞은 경우(`matched: true`), 자식이 종료된 경우(`child_exited: true`). 이것만으로 자식이 조용해졌다는 뜻은 **아닙니다** — 정규식 일치는 조용한 구간 없이 이것을 켜므로, 60초 settle 창의 0.45s 지점에 `settled: true`가 실린 응답이 나올 수 있습니다.

  조용함을 뜻할 때도, 조용함의 원인은 세 가지이고 이것만으로는 구별할 수 없습니다: 턴이 끝난 것, 자식이 사람을 기다리는 것, 또는 **자식이 긴 명령을 백그라운드로 돌리고 출력을 멈춘 것**. 세 번째가 물리는 경우입니다: busy 마커가 사라지기를 폴링하던 호출자가 그것이 없는 프레임을 읽고 일이 끝났다고 판단했는데, 실제보다 260초 전이었습니다. 무언가의 *부재*로 판단한다면 `settled`만으로는 증거가 부족합니다.
- `timed_out: true` — `--timeout-ms`에 먼저 도달했습니다. 실패가 아니라 결과입니다.
- `matched: true` — `--wait-for-regex`가 맞았습니다.
- `child_exited: true` — send가 진행 중일 때 자식이 끝났습니다.
- `busy_at_send: true` — 이 send가 도착했을 때 자식이 *아직 출력을 내고 있었으므로*, 응답에 이전 턴의 꼬리가 들어 있을 수 있습니다. 답이 이전 질문의 것처럼 보이면 확인할 가치가 있습니다.
- `regex_timed_out: true` — `--wait-for-regex` 패턴이 매칭 예산을 넘어서 포기되었습니다. 거의 항상 치명적으로 백트래킹하는 패턴입니다; 단순화하세요.
- `dropped_bytes` — 로그가 더 이상 들고 있지 않은 이전 출력의 양입니다: 로테이션되어 나갔거나, 트랜스크립트 write가 실패해서 잃은 것입니다. `--since` 커서를 무효로 만들지는 **않습니다**: 커서는 절대 위치를 유지하므로, drop 이전의 커서는 오류 대신 그 이후에 아직 들고 있는 전부를 반환합니다. drop된 영역 안에 떨어지는 커서는 그 영역 다음에 온 출력으로 해석됩니다 — 이미 전달된 출력으로는 절대 가지 않습니다, 이미 전달된 출력이 오면 현재 턴의 새 출력처럼 보일 것이기 때문입니다.
- `transcript_gap_bytes` — `status`와 `send` 응답에만 있고, 어떤 write도 기록하지 못한 출력이 아직 남아 있을 때만입니다. 어긋남이 디스크에 없는 유일한 구간입니다: 다음 성공한 write가 그것을 기록하고, `read`는 대신 `dropped_bytes`로 보고합니다.
- `screen_rows`, `screen_cols`, `screen_size_recorded` — `--screen`과 함께일 때만입니다: 화면이 렌더된 geometry와, 그 geometry가 자식의 기록된 winsize인지 fallback인지를 나타냅니다.
  [자식이 실제로 돌아가는 크기로 렌더합니다](#자식이-실제로-돌아가는-크기로-렌더합니다)를 보세요.

### `child_busy`와 `idle_ms`는 `read`에 있지, `send`에 있지 않습니다

자식이 settle 창 안에서 무언가를 출력했는지, 그리고 마지막으로 출력한 지 얼마나 됐는지입니다. "아직 일하고 있는가"의 구조화된 형태입니다: 상대 UI에서 busy 마커를 grep하지 말고 이것을 쓰세요, 그쪽은 표현이고 예고 없이 바뀝니다.

**`read`와 `list`의 필드이지, `send` 응답의 필드가 아닙니다.** `send`는 이미 자식이 settle할 때까지 막혀 있었으므로, 그다음에 물으세요:

```console
$ rune session send --name grok --settle-ms 2500 "run the suite"
$ rune session read --name grok --tail 1 --json     # child_busy, idle_ms
```

이 문서는 예전에 둘 다 `send` 응답의 필드로 적었는데, 가장 중요한 방식으로 틀린 것입니다 — `send`에서 `.child_busy`를 읽는 호출자는 `nil`을 받고 UI를 grep하는 쪽으로 돌아가며, 그것이 바로 이 필드들이 대체하려고 존재하는 일입니다.

이름이 말하는 것은 자식이 *출력 중*이라는 것이지, *일하고 있다*는 것이 아닙니다: 명령을 백그라운드로 돌리고 조용해진 자식은 `child_busy: false`를 보고합니다.

### 긴 트랜스크립트에서 무언가를 찾기

원하는 것이 가운데 있을 때는 `--since`와 `--tail`이 도움이 되지 않습니다. 에이전트를 몰아 하루 일한 결과는 379KB에 닿았습니다.

```console
$ rune session read --name grok --grep 'THE BOARD' --context 2
```

raw 스트림이 아니라 정리된 텍스트에 맞춥니다. 전체 화면 에이전트의 다시 그리기 프레임이 이스케이프 시퀀스 사이로 단어를 쪼개기 때문입니다 — 화면에서 분명히 보이는 패턴이 바이트에는 맞지 않습니다. 응답에는 `grep_matches`가 실립니다.

**cleaned는 rendered가 아니고, 그 차이는 세션이 다루려고 존재하는 바로 그 자식들에서 뭅니다.** cleaned 텍스트는 이스케이프를 제거한 전체 다시 그리기 스트림이므로: 덮어쓰인 히스토리도 여전히 맞고, 화면이 그 뒤로 보여 주지 않은 깨끗한 단독 줄로 돌아옵니다; 커서로 그린 프레임에는 줄바꿈이 전혀 없어서 grep 한 줄이 되고, `--context`는 아무 일도 하지 않으며, 일치 하나가 그럴듯해 보이는 `grep_matches: 1` 아래 프레임 전체를 돌려줍니다; 그리고 화면에서 보이는 것에 고정한 패턴은 `grep_matches: 0`을 돌려줄 수 있습니다, 화면에서의 인접이 스트림에서의 인접이 아니기 때문입니다. 지금 화면에 무엇이 보이는지가 질문이라면 `--screen`을 쓰세요. `--grep`은 긴 트랜스크립트에서 한 줄을 찾는 용도이고, 그것이 잘하는 일입니다.

컴파일되지 않는 패턴은 예외가 아니라 `grep_error`로 돌아오고 **아무것도 고르지 않습니다**: `output`과 `clean_output`은 비어 있고 `grep_matches`는 없습니다, 이것이 "필터가 돌지 않았다"와 "필터가 아무것도 찾지 못했다"를 구별하는 방법입니다. read 자체는 여전히 성공하므로 `cursor`, `prompt_detected`, `child_busy`는 모두 그대로 있습니다 — 어느 것도 패턴에 의존하지 않고, 앞으로 가려면 cursor가 필요합니다. (`send --wait-for-regex`는 다릅니다: 그쪽은 패턴이 반환 시점을 정하므로, 나쁜 패턴은 처음부터 거부됩니다.)

### `prompt_detected`는 참고용일 뿐입니다

모든 `send`/`read` 결과에는 `prompt_detected`가 실려 있지만, **그것으로 게이트하지 말고**, 어느 쪽으로 실패하는지만 알아 두세요.

실제 출력으로 측정하면, 일반 텍스트에서는 `false`, 맨 `$ `에서는 `false`, **`Do you want to proceed?`에서는 `false`**, `❯ `에서는 `true`입니다. 그래서 grok에서는 거의 모든 read에서 `true`입니다, grok의 composer가 항상 `❯`로 끝나기 때문입니다 — 한 호출자는 8번 중 8번 `true`인 것을 보고 아무것도 가리지 못한다고 판단했습니다. 가리기는 합니다; 다만 프롬프트 형태의 마지막 줄을 감지할 뿐이고, 그것은 "나를 기다리는가"와 같은 질문이 아닙니다. 위의 세 번째 경우를 보세요: 가장 잡고 싶은 바로 그 권한 대화상자에서 `false`입니다. 그건 화면을 보세요. rune의 프롬프트 패턴은 셸 형태의 프롬프트(`user@host:~$`, `[y/N]`, `Password:`)에 맞고, 일부러 보수적입니다. 에이전트 REPL은 대체로 그중 어느 것도 아니므로, 다루고 싶은 바로 그 CLI에서는 보통 `false`입니다. 프롬프트를 기다리면 실제 대상 대부분에서 멈춥니다 — 그래서 settle-time이 기본 신호입니다.

## 트랜스크립트 읽기

`read`는 세션의 지속 트랜스크립트를 다시 재생하며, 세션이 살아 있든 이미 멈췄든 같게 동작합니다:

```console
$ rune session read --name grok --tail 50
$ rune session read --name grok --since 41234     # page from a cursor a previous call returned
```

모든 세션은 `rune watch`가 만드는 것과 같은 형식의 NDJSON 이벤트 로그를 쓰므로, 다른 pane에서 살아 있는 세션을 따라갈 수 있습니다:

```console
$ tail -f ~/.rune/projects/<project>/sessions/grok/output.ndjson
```

전체 화면 TUI 에이전트는 ANSI 다시 그리기 트래픽을 많이 만들므로, 트랜스크립트 전체를 읽기보다 `--tail`/`--max-output`을 쓰세요.

`--max-output=BYTES`는 앞부분과 뒷부분을 남기고, 이음새를 텍스트 자체에 표시합니다:

```
...the last line before the cut
[rune] ==== 41233 bytes omitted by --max-output ====
the first line after it...
```

그 줄이 없으면 응답은 자식이 출력한 적 없는 연속된 출력처럼 읽힙니다 — 측정해 보면, 201바이트 트랜스크립트를 `--max-output=200`으로 잘랐을 때, `chsh -s /bin/zsh`를 `chsh -s bin/zsh`로 바꾼 그 한 바이트가 빠졌습니다, 다르지만 여전히 그럴듯한 경로입니다. 마커는 트랜스크립트가 아니라 rune의 주석이므로 BYTES에 잡히지 않고, 응답이 예산을 조금 넘을 수 있습니다; `truncated`와 `omitted_bytes`가 권위 있는 답입니다, 자식은 무엇이든 출력할 수 있고, 마커처럼 보이는 줄도 포함하기 때문입니다.

### `--screen`: 도착한 것이 아니라 터미널이 보여 주는 것

전체 화면 에이전트에서는 보통 이 필드가 원하는 것입니다. 바이트 스트림에는 모든 다시 그리기의 모든 프레임이 들어 있고 답이 그 사이에 쪼개져 있습니다; screen에는 표시된 것만 들어 있습니다.

```console
$ rune session send --name grok --screen -- "reply with just the branch name"
$ rune session read --name grok --screen
```

grok를 상대로 측정하면, 361KB 트랜스크립트가 1.1KB screen으로 렌더되었고, 에이전트가 분명히 보여 준 답은 **3턴 중 3턴에서 바이트 스트림에는 없었고 렌더된 screen에는 3턴 중 3턴에서 있었습니다.** 내용으로 맞출 거면 `screen`에 맞추세요.

아닌 것이 세 가지입니다. 끝 상태이므로 스크롤되어 나간 것은 사라집니다 — 트랜스크립트가 일어난 일의 기록으로 남습니다. opt-in인 이유는 화면을 그리는 자식에게만 의미가 있기 때문입니다: cooked-mode 셸에서는 바이트 스트림이 이미 답입니다. 그리고 **read 필터로 잘리지 않습니다** — `--since`, `--tail`, `--grep`, `--max-output`은 모두 `output`/`clean_output`을 자르고 `screen`은 그대로 둡니다. 잘리기는 합니다, 다만 geometry로입니다: 최대 `screen_rows x (screen_cols + 1)`이고, 둘 다 같은 응답에 돌아옵니다. 219,941바이트 트랜스크립트는 약 2KB로 렌더됩니다. 그래서 `--max-output=200 --screen`은 잘린 응답을 주지만, 당신이 이름 붙이지 않은 규칙으로 잘립니다.

### 자식이 실제로 돌아가는 크기로 렌더합니다

세션의 자식은 40x120으로 시작하고, `attach`가 넘겨받은 터미널 크기로 리사이즈합니다 — 그래서 크기는 상수가 아니고, 고정된 크기로 렌더하면 아무도 본 적 없는 화면이 나옵니다. supervisor는 자식의 현재 winsize를 바꿀 때마다 `meta.json`에 기록하고, `--screen`은 그 크기로 렌더한 뒤 그것을 돌려줍니다:

```console
$ rune session read --name grok --screen --json | jq '{screen_rows, screen_cols, screen_size_recorded}'
{ "screen_rows": 30, "screen_cols": 100, "screen_size_recorded": true }
```

처음부터 끝까지 측정했고, pyte 0.8.2와 GNU screen 4.00.03이 같은 바이트를 독립 오라클로 재생했습니다(모든 형태에서 서로 정확히 일치했습니다):

| 무엇을 구동했는가 | 이전에 틀린 행 | 이후에 틀린 행 |
|---|---|---|
| control socket으로 30x100 리사이즈, 자식이 WINCH에서 다시 그림 | 36/37 | **0/31** |
| 같은 것을 24x80에서 | 30/31 | **0/25** |
| 같은 것을 12x40에서 | 18/19 | **0/13** |
| 같은 것을 50x200에서 | 50/51 | **0/51** |
| 같은 것을 40x120에서(크기가 우연히 일치) | 0/41 | 0/41 |
| 30x100 pty에서 진짜 `rune session attach`, 자식이 WINCH를 무시 | 29/30 | **0/30** |

attach 행에서 오라클에는 그 터미널이 받은 바이트가 들어갔으므로, "0 of 30"은 rune이 렌더한 화면이 사람이 보고 있던 것과 행마다 일치했다는 뜻입니다.

**`screen_size_recorded`가 진짜 geometry와 fallback을 구별하는 방법입니다 — 숫자가 아닙니다.** 40행 터미널에서 attach한 세션은 fallback이 쓰는 것과 똑같은 40x120을 기록하므로, 숫자 쌍만으로는 구별이 실리지 않습니다. `screen_size_recorded`는 보고된 크기가 `meta.json`이 실제로 들고 있던 값일 때만 true입니다. false인 경우는 세 가지이고, 모두 40x120을 보고합니다:

- 아무도 리사이즈하지 않은 세션. supervisor는 pty를 40x120으로 설정하고 기록하지 않으므로, 여기 fallback은 추측이 아닙니다 — 자식이 정말로 돌아가는 크기입니다.
- rune이 크기를 기록하기 전에 쓰인 세션 디렉터리.
- 쓸 수 있는 터미널이 아닌 기록된 크기, 할당하지 않고 버리거나 clamp합니다: `meta.json`은 디스크의 파일이고 그리드는 미리 만들기 때문입니다.

컨트롤 소켓으로 도착하는 리사이즈는 300x1000으로 clamp됩니다 — 실제 터미널을 넘는 값입니다 — 그리고 clamp는 pty와 기록 모두에 적용되므로, 자식과 기록과 렌더는 항상 같습니다. pty의 winsize 필드는 16비트이고, 기록된 65535x65535는 이후 모든 `--screen`이 그 크기 그리드를 몰게 했을 것입니다: 일부러 적대적인 683KB 트랜스크립트에서, `read --screen` 한 번은 40x120에서 0.76s, 상한에서 3.41s, clamp 없이 17.72s가 듭니다.

**리사이즈 경우 하나가 미해결입니다.** 보유한 트랜스크립트 전체가 자식의 현재 크기로 렌더되므로, geometry가 중간에 바뀌면 바뀌기 전에 그려진 출력이 새 크기로 다시 흐릅니다. 전체 화면 에이전트에서는 이것이 맞고, 증명도 됩니다: TUI는 SIGWINCH에서 다시 그리고, attach 때 supervisor는 백로그를 터미널 크기로 터미널에 재생합니다, 그것이 바로 전체 트랜스크립트를 그 크기로 렌더하는 것과 같습니다 — 위의 0-of-30 attach 행은 SIGWINCH를 완전히 무시하는 자식에서도 성립합니다. 한 번만 그리고 다시 그리지 않는 자식의 pty가 *이미 attach된 터미널 아래에서* 리사이즈되는 경우는 미해결입니다, 그 터미널은 이미 그린 글리프를 다시 흐르게 하고, 맞출 참조 답이 없기 때문입니다. 그런 스트림에서 중간에 40x120에서 24x80으로 줄이면, GNU screen은 커서 행만 남기고, pyte는 아무것도 남기지 않으며, 둘이 남긴 얼마 안 되는 것 중 한 행에서 서로 어긋났습니다. rune은 내용을 남기고 다시 흐르게 하므로 둘 다와 다릅니다. 예전 고정 크기로 렌더하면 그쪽에서 순수 행 수는 더 나았습니다(24 대비 15가 틀림), 다만 거의 빈 화면이 거의 빈 오라클과 우연히 맞았기 때문이지, 누구에게든 더 진실한 것을 보여 줬기 때문이 아닙니다.

**마지막 512KB에서 렌더되며, 어떤 에이전트에서는 그 비용이 눈에 보입니다.** 4.5MB에 걸친 grok 출력 조사에서 절대 커서 이동 109,364개, 동기화 업데이트 괄호 31,798개, 어떤 종류의 erase도 **0**개였습니다 — `\e[K`도, `\e[2K`도, `\e[2J`도, 스크롤 영역도 없었습니다. 위치만 잡고 덮어써서 다시 그리는 에이전트는 터미널이 얼마나 오래됐든 쓴 모든 셀을 기억하기를 기대합니다. 윈도우에서 렌더하면 빈 그리드에서 시작하므로, 한 번만 그리고 다시 그리지 않은 것 — 헤더, 배너 — 은 그냥 없고, rune은 빠진 줄도 모릅니다. `--screen`을 더 자주 읽어도 도움이 되지 않습니다; 윈도우는 시간이 아니라 바이트로 잽니다.

같은 조사가 더 미묘한 점도 설명합니다. 에이전트가 한 번도 erase하지 않으면, 화면의 중복 줄이 완전히 충실한 것일 수 있습니다: 레이아웃이 한 행 아래로 밀리고 새 위치에 다시 그리면, 옛 복사본을 지울 것이 없고, **실제 터미널도 그 중복을 보여 줍니다.** 반복된 줄을 rune 버그로 보기 전에, 에이전트가 무엇이든 erase하는지부터 확인하세요.

### 알려진 한계: 폴링한 `--screen`이 반만 그려진 프레임을 돌려줄 수 있습니다

실제 사용에서 보고되었고, **고쳐지지 않았습니다.** 다시 그리는 에이전트에서 `--screen`을 폴링하면 가끔 다시 그리기 중인 프레임이 돌아옵니다 — 보고된 경우에는 한 줄이 인접한 두 행에 중복되었습니다.

후보 수정 두 가지를 측정하고 버렸습니다. 연속 렌더를 비교해 반복된 것만 반환하는 방식은 아무것도 하지 않는 것보다 **나빴습니다** — 찢긴 프레임이 20개 중 13개 대 11개였습니다 — 주기로 그리는 에이전트는 같은 프레임을 두 번 렌더하는 일이 드물어서, 검사가 타임아웃되고 찢긴 프레임을 그대로 돌려주기 때문입니다. 안정성을 정적 상태로 다시 정의하는 쪽은 찢김을 전혀 재현하지 못했습니다: 같은 자식이 한 번은 11/20, 두 번은 0/20을 냈고, 그건 하네스가 보이는 것을 재고 있지 않았다는 뜻입니다. "끝난 것처럼 보이는" 쪽으로 조용히 실패하는 수정은, 감안하고 계획할 수 있는 한계보다 나쁩니다.

**어떻게 할지.** 되돌릴 수 없는 결정에 렌더된 프레임 하나를 권위로 삼지 마세요. 값을 읽는 중이면 두 번 폴링하고 일치할 것을 요구하세요. 마커를 기다리는 중이면, `--screen`이 스냅샷인 곳에서 `--wait-for-regex`는 결정적입니다.

**rune 탓이 아닐 수 있습니다.** 한 에이전트의 출력 4.5MB를 조사하니 어떤 종류의 erase도 0개였고, 한 번도 erase하지 않고 레이아웃을 옮기는 에이전트는 옛 복사본을 화면에 남깁니다 — 실제 터미널도 그 중복을 보여 줍니다. rune의 렌더러는 그 조사로 만든 여섯 프로필에서 독립 에뮬레이터와 일치합니다. 중복 줄을 rune 버그로 올리기 전에, 에이전트가 무엇이든 erase하는지부터 확인하세요.

### 트랜스크립트는 한계가 있습니다

파일과 supervisor의 메모리 모두 상한이 있으므로, 하루 동안 켜 둔 세션이 한없이 커지지 않습니다. 파일 상한은 두 번 강제됩니다: 평소에는 로테이션으로, 그리고 — 디렉터리가 쓸 수 없게 되거나 디스크가 계속 가득 차서 로테이션이 전혀 성공할 수 없을 때는 — 상한의 두 배인 하드 천장으로, 그 너머의 출력은 쓰지 않고 dropped로 기록합니다. 어느 쪽이든 `read`는 `dropped_bytes`를 보고하고 커서는 절대 위치를 유지합니다. 로테이션이 옛 출력을 버리면, `read`는 `dropped_bytes`를 보고하고 커서는 절대 위치를 유지합니다 — 커서는 여전히 스트림의 같은 위치를 가리키고, 다만 더 이상 들고 있지 않은 출력을 가리킬 뿐입니다.

트랜스크립트 write가 실패하면 — 가득 찬 디스크, 쓸 수 없는 디렉터리 — 출력은 같은 방식으로 버려집니다, 다만 그 뒤에 이어지는 스트림의 *한가운데*일 때는 다릅니다. 그 바이트는 들고 있다가 쓰기가 재개되는 즉시 기록되고, 커서는 하나의 누적 합을 건너뛰지 않고 각 dropped 영역을 통과해 매핑되므로, 구멍 앞의 출력이 새것처럼 다시 전달되지 않습니다. write가 성공할 때까지는 구멍을 기록할 디스크 자리가 없고, 그것이 `status`의 `transcript_gap_bytes`가 보고하는 것입니다.

## 실제 에이전트를 다루기 전에 알 것

- **`start`는 *supervisor*가 준비됐을 때 반환하지, 자식이 준비됐을 때가 아닙니다.** 에이전트 CLI는 부팅에 몇 초가 걸리고, 듣기 전에 보낸 입력은 그냥 사라집니다. 막 시작한 세션을 다루기 전에 준비 마커를 기다리세요 — `read`를 폴링하거나, 첫 `send`를 `--wait-for-regex`로 하세요.
- **settle은 휴리스틱입니다.** 답 중간에 `--settle-ms`보다 오래 멈추는 자식은 잘린 응답을 돌려줍니다. 값을 올리거나, `--wait-for-regex`를 쓰세요.
- **`--wait-for-regex`는 턴 전체가 아니라 가장 최근 256 KB를 봅니다.** 32768자까지의 일치는 항상 찾고, 그보다 길어야 하는 일치는 절대 찾지 않습니다. 메가바이트를 감싸는 패턴이 아니라 마커를 기다리세요.
- **1024바이트 이상인 한 줄은 cooked-mode 자식 안으로 사라집니다.** 그것은 `MAX_CANON`이고, rune의 한계가 아니라 터미널 한계입니다: 라인 규율이 그보다 긴 canonical 줄을 조립하지 못하고 조용히 버립니다 — 1023바이트는 도착하고, 1024바이트는 도착하지 않습니다. 대부분의 에이전트 CLI는 터미널을 raw mode로 돌려서 영향을 받지 않습니다(300KB가 바이트 단위로 그대로 도착합니다). 인터랙티브 셸도 같습니다: `bash --norc -i`는 readline을 쓰고, readline이 터미널을 raw mode로 바꾸며, 1995자 줄을 바이트 단위로 그대로 받습니다. 이 한계는 *cooked mode*로 읽는 자식을 뭅니다 — 맨 `cat`, 또는 readline 없이 stdin을 읽는 스크립트입니다. 쪼개서 보내거나, raw-mode 대상을 다루세요.
- Enter는 캐리지 리턴으로 보내지며, 실제 터미널이 보내는 것이므로 raw-mode TUI가 받습니다. cooked-mode 셸은 영향을 받지 않습니다.
- 자식의 pty에는 명시적인 창 크기가 주어집니다, 분리된 세션에는 복사할 터미널이 없고 설정되지 않은 pty는 0x0이라서 — 전체 화면 에이전트가 허공에 렌더하게 되기 때문입니다. 40x120으로 시작하고, attach된 터미널이 붙어 있는 동안 그것을 따라가며(상한 300x1000), 마지막 하나가 떠나면 40x120으로 돌아갑니다. `--screen`은 그중 현재인 크기로 렌더합니다.

## 상태가 있는 곳

`RUNE_HOME`(기본값 `~/.rune`), 소유자만 접근할 수 있는 권한입니다:

```
$RUNE_HOME/projects/<project>/
  sessions/<name>/
    meta.json        0600   pid, supervisor pid, command, state, child terminal size
    output.ndjson    0600   full transcript
    supervisor.log   0600   supervisor stderr, for when something goes wrong
    control.sock     0600   the supervisor's control socket
  archive/<stamp>-<name>/   archived sessions, out of the live namespace
```

세션을 격리하려면 `RUNE_HOME`을 설정하세요(테스트, 샌드박스, 병렬 작업).

`meta.json`은 rename으로 교체되며, 제자리에서 truncate되지 않습니다, 다른 모든 rune 프로세스가 잠금 없이 이것을 읽어 "이 세션이 있는가, 살아 있는가?"에 답하기 때문입니다. 짧아진 구간이 있으면 `send`가 "No such session"이라고 답하고 `list`가 `state: dead`를 보고하는 구간이 됩니다; 자식의 winsize를 기록하면서 리사이즈마다 쓰는 일이 되었고, 사람이 창 가장자리를 끌면 프레임마다 하나가 나갑니다. 실제 attach를 7.5초 동안 250개 창 형태에 걸쳐 끌면서, 다른 프로세스가 meta를 빡빡한 루프로 읽는 것으로 측정했습니다: 이전에는 294,728번 read 중 90번이 읽을 수 없었고, 이후에는 312,582번 중 0번이었습니다.

## 여러 개를 한꺼번에 돌리는 비용

세션 하나가 supervisor 프로세스 하나이고, 그 격리는 의도된 것입니다: 끼인 에이전트는 자기 세션만 내리고 나머지는 건드리지 않습니다. 값은 세션마다 Ruby 인터프리터 하나이고, 펼치기 전에 알아 둘 만합니다.

측정, idle 상태의 자식으로:

| 세션 | 상주 메모리 | 디스크립터 |
|----------|-----------------|-------------|
| 24 | 543 MB | 648 |
| 60 | 1361 MB | 1620 |

세션당 약 **23 MB와 디스크립터 27개**이고, 평평합니다 — 60개일 때도 24개일 때와 같고, send 라운드를 걸쳐도 변하지 않습니다. 그래서 비용은 놀랍기보다 예측 가능하고 선형이지만, 앞에서 한꺼번에 나갑니다: 에이전트 60개는 그중 어느 것도 아무것도 하기 전에 이미 1기가바이트를 훨씬 넘습니다.

동시성 자체는 같은 테스트에서 버텼습니다: 동시 `start` 60개가 모두 성공했고, 모든 `send`가 보낸 세션에 닿았고, `list`가 현실과 맞았고, 이후에 남은 것도 없었습니다. 같은 도구에 `--name` 없이 동시 `start` 호출 30개는 서로 다른 코드명 30개를 냈고 충돌은 없었습니다.

## 범위

rune은 세션 **브로커**이지, 메시지 버스가 아닙니다. 세션을 들고 이름으로 주소를 붙입니다; 누가 누구와 말할지는 호출하는 에이전트의 일입니다 — 그 에이전트는 이미 이름을 가지고 있습니다. 세션 사이 라우팅, 에이전트별 프로필, 공유 대화 로그는 일부러 범위 밖입니다.
