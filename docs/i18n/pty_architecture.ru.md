# Архитектура Pseudo-TTY (PTY) и TTY в Rune

> **Руководство для разработчиков и ИИ-агентов**  
> *Как Ruby управляет псевдотерминалами, интерактивными потоками и автоматизацией приглашений в `rune`.*

---

## 1. Обзор: что такое Pseudo-TTY (PTY)?

Когда программа выполняется в обычной подоболочке или в канале подпроцесса (например, `IO.pipe` или стандартный запуск в подоболочке), ОС подключает стандартные каналы для `stdin`, `stdout` и `stderr`. Многие CLI-программы (такие как `git`, `docker`, `python`, `zsh`, `sudo`) определяют, является ли `stdout` терминалом (с помощью `isatty()`), и отключают цвета, форматирование приглашения или построчную буферизацию, если это не так.

**Pseudo-TTY (PTY)** — это пара виртуальных терминальных устройств уровня ядра, master и slave:
- **Slave PTY**: подключается к дочернему процессу как его управляющий терминал (`tty`). Дочерний процесс считает, что работает внутри настоящего терминала (например, iTerm2 или xterm).
- **Master PTY**: принадлежит `rune` (`PTYRunner`). `rune` читает вывод дочернего процесса и записывает клавиатурный ввод непосредственно в дескриптор master.

```
+------------------+         Master PTY          Slave PTY         +-------------------+
|  Rune PTYRunner  | <=======================> (Virtual Terminal) <==> |  Child Process    |
| (Agent / Human)  |    (reader / writer IO)                       | (bash, git, etc.) |
+------------------+                                               +-------------------+
```

## 2. Выполнение PTY в Ruby (`PTY.spawn`)

Стандартная библиотека Ruby предоставляет `require 'pty'`. `rune` использует `PTY.spawn` внутри `lib/rune/pty_runner.rb`:

```ruby
PTY.spawn(env, command) do |reader, writer, pid|
  # reader: IO object to read output from slave PTY
  # writer: IO object to write stdin into slave PTY
  # pid:    Process ID of child process
end
```

### Неблокирующее чтение порциями (`readpartial`)

Стандартное построчное чтение (`reader.each_line`) блокируется до получения символа новой строки (`\n`). **Интерактивные приглашения** (такие как `Password: `, `Select option [y/N]` или `user@host:~$ `) **не заканчиваются символом новой строки**. Если читать через `each_line`, родительский процесс блокируется в ожидании `\n`, пока дочерний процесс сидит в ожидании пользовательского ввода — это приводит к **взаимоблокировке**.

Чтобы исключить взаимоблокировки, `rune` читает порции с помощью `readpartial(4096)`:

```ruby
loop do
  # Bounded wait rather than a bare readpartial, so signals and the timeout
  # are still serviced while the child is quiet.
  next unless reader.wait_readable(0.2)

  chunk = reader.readpartial(4096)
  output_buffer << chunk
  on_output&.call(chunk) # Real-time streaming callback (NDJSON / TTY)
  script_step_index = process_script_steps(script_step_index, output_buffer, writer) if script
end

# prompt_detected is computed once at the end, from the LAST non-blank line
# only — not "did any line ever look like a prompt". A run that printed a
# prompt and then kept going is not waiting for input, so the any-line form
# answered a question nobody was asking.
prompt_detected = detect_prompt?(output_buffer.lines.reverse.find { |line| !line.strip.empty? })
```

Когда дочерний процесс завершается, slave PTY закрывается, и `readpartial` возбуждает `Errno::EIO` или `EOFError`, которые `rune` перехватывает, чтобы завершиться корректно.

## 3. Санобработка ANSI и двойной вывод (для человека и для агента)

`rune` перехватывает необработанные ANSI-последовательности терминала (цвета, перемещения курсора, очистку экрана).

- **Для людей (режим TTY)**: необработанный вывод форматируется через `Renderer.render_tty` с полноценным цветом и интерактивным форматированием.
- **Для ИИ-агентов (режим JSON)**: вывод обрабатывается через `Parsers::TextSanitizer.strip_ansi(raw_output)`, чтобы убрать ANSI-коды и вернуть чистый текст для экономии токенов LLM. Это верно без оговорок только без `--max-output`: этот флаг ограничивает оба поля независимо одним и тем же бюджетом байт, так что после этого они описывают разные окна выполнения, и `clean_output` перестаёт быть равен `strip_ansi(raw_output)`:

```ruby
# Strips SGR ANSI color codes, cursor escape codes, and terminal controls
ANSI_REGEX = /\e\[[0-9;]*[a-zA-Z]/
clean_output = text.gsub(ANSI_REGEX, '')
```

## 4. Логика определения приглашения (`Parsers::PromptDetector`)

Чтобы понять, завершилась ли команда или сидит на интерактивном приглашении, `Parsers::PromptDetector` анализирует потоковые фрагменты строк:

### Поддерживаемые сигнатуры приглашений:
- Приглашения shell PS1: `user@host:~$ `, `bash-5.2# `, `➜  rune git:(main)`, `❯ `
- Меню и интерактивный выбор: `Select:`, `[y/N]`, `(y/n)?`, `Password: `

Две сигнатуры, про которые этот список раньше утверждал, что они **не** распознаются, — на самом деле были не добавлены, а удалены, потому что консервативность детектора намеренная: `Select an option: ` (шаблон вопроса заякорен, поэтому он совпадает с `Select:`, но не с предложением, заканчивающимся двоеточием) и `(venv) λ ` (`λ` не входит в класс глифов приглашения, которым являются `➜ ❯ ›`).

### Отклонение ложных срабатываний:
`PromptDetector` игнорирует строки, содержащие сравнения в коде (`if x > 5`) или присваивания переменных оболочки (`export PATH=$PATH`). Цитата markdown вроде `> quote` тоже отклоняется, но потому что не совпадает ни с одним положительным шаблоном, а не из-за исключения — исключение для blockquote срабатывает только на строке, которая также содержит текст в угловых скобках.

## 5. Движок автоматизации сценариев (`Rune::Script`)

`rune` позволяет определять интерактивные DSL-сценарии для автоматизации многошаговых PTY-программ:

```ruby
script = Rune::Script.define do
  wait_for(/Select a target environment/)
  send_keys "production\n"
  pause 0.5
  wait_for(/Are you sure\? \[y\/N\]/)
  send_keys "y\n"
end

Rune::PTYRunner.new('deploy-tool', script: script).run
```

Движок сценариев обрабатывает шаги за один неблокирующий проход, поэтому `send_keys` сразу пишет в `writer`, не дожидаясь последующих порций.

## 6. Живая интерактивная сквозная передача (`PTYWatcher` / `rune watch`)

`PTYRunner` буферизует весь вывод команды и возвращает управление только после её завершения: это правильно для скриптов и захвата вывода, но не подходит, когда нужно реально сидеть за клавиатурой и управлять интерактивной программой, пока за сеансом кто-то ещё наблюдает. `PTYWatcher` (`lib/rune/pty_watcher.rb`) — отдельный класс именно для этого живого, двунаправленного случая, а не режим, прикрученный к `PTYRunner`: модель выполнения (raw-режим терминала, фоновый поток пересылки ввода) достаточно отличается, чтобы не помещаться туда, а контракт `PTYRunner` «запустить, захватить, вернуть один раз» остаётся неизменным.

### Raw-режим терминала (`io/console`)

Чтобы клавиши со стрелками и другой однобайтовый ввод или ввод escape-последовательностями вообще доходили до дочернего процесса, собственный управляющий терминал родительского процесса должен выйти из cooked mode, в котором ядро буферизует ввод построчно и локально эхо-повторяет нажатия, пока не придёт символ новой строки. `io/console` (подключается явно, а не подтягивается неявно через `pty`) добавляет `IO#raw`, которым `PTYWatcher#with_raw_input` оборачивает весь сеанс пересылки:

```ruby
def with_raw_input(&block)
  entered = false
  @input.raw do
    entered = true
    block.call
  end
rescue Errno::ENOTTY, NoMethodError
  raise if entered   # only fall back if raw-mode *entry* itself failed

  block.call
end
```

Флаг `entered` важен: как только raw mode действительно включён, постороннее исключение из глубины сеанса (например, сломанный output sink) должно распространяться обычным образом, а не трактоваться как «raw mode isn't supported» и молча повторно запускать уже порождённый сеанс второй раз.

### Двунаправленная пересылка

В отличие от единственного цикла чтения у `PTYRunner`, `PTYWatcher` параллельно выполняет две вещи: фоновый поток пересылает реальные нажатия клавиш человека в PTY дочернего процесса по мере их поступления (`forward_input`), а основной поток опрашивает вывод дочернего процесса и сразу же передаёт его на экран (`pump_output`), вместо того чтобы накапливать его в буфере, который возвращается только в конце.

Оба пути декодируют через `UTF8StreamDecoder`, который удерживает незавершённый суффикс UTF-8 между вызовами `readpartial`. Поэтому допустимый многобайтовый символ сохраняется, даже если ядро разрезает его между порциями; по-настоящему неверные или финальные незавершённые последовательности по-прежнему становятся символами замены.

`PTYWatcher` также зеркалирует текущий размер управляющего терминала в строках и столбцах на PTY дочернего процесса. Он перепроверяет это в цикле опроса вывода, поэтому изменённый размер терминала доходит до дочернего процесса без небезопасной работы внутри signal trap.

```
+------------------+   keystrokes    +------------------+   output    +-------------------+
|  Human terminal  | --------------> |  PTYWatcher       | ----------> |  Real terminal      |
|  (raw mode)      |  (bg thread)    |  (master PTY)     |  (live)     |  screen + NDJSON log |
+------------------+                 +------------------+             +-------------------+
```

### Журнал событий NDJSON

Каждая порция, дошедшая до экрана, также записывается как событие NDJSON в файл журнала (по умолчанию — объявленный, устойчивый к коллизиям временный файл с правами `0600`, либо `--log=PATH`), чтобы AI-агент мог смотреть сеанс вживую через `tail -f`, не попадая JSON-шумом в собственный терминал человека:

```json
{"event":"start","command":"...","pid":12345}
{"event":"output","bytes":42,"text":"..."}
{"event":"exit","exit_code":0}
```

Намеренно не stderr по умолчанию: stderr делит терминал человека с живым пробросом, и реальное использование сразу показало, что вплетение JSON в интерактивный сеанс делает его нечитаемым.

Если output sink закрывается с `EPIPE`, `PTYWatcher` убивает дочерний процесс и выполняет reap, прежде чем вернуть структурированный сбой, не давая отсоединённому интерактивному процессу пережить watcher.

## 7. Обработка ошибок и коды выхода

И `PTYRunner`, и `PTYWatcher` унифицируют коды выхода Unix для пограничных случаев:

| Условие | Код выхода | Обработка |
| :--- | :--- | :--- |
| Штатное завершение | `status.exitstatus` | Чистое завершение |
| Команда не найдена | `127` | Перехватывает `Errno::ENOENT` |
| Отказано в доступе | `126` | Перехватывает `Errno::EACCES` |
| Таймаут выполнения (только `PTYRunner`) | `124` | Перехватывает `Timeout::Error`, затем посылает `SIGKILL` и выполняет reap дочернего процесса — `Timeout.timeout` прерывает только собственный поток управления Ruby, а не порождённый процесс ОС |
| Дочерний процесс убит (сигнал) | `128 + sig` | Сигналы вроде `SIGKILL` (137) или `SIGTERM` (143) |

## Резюме для разработчиков

`rune` объединяет:
1. `PTY.spawn` для настоящей эмуляции терминала.
2. `readpartial` для чтения потока без взаимоблокировок.
3. `UTF8StreamDecoder` плюс `TextSanitizer` для безопасного на границах, чистого агентского JSON.
4. `PromptDetector` для умных проверок интерактивности.
5. `Script` DSL для пошагового автоматизированного ввода.
6. `PTYWatcher` + `io/console` raw mode для живых двунаправленных сеансов под управлением человека с журналом NDJSON, доступным агенту через `tail`.
